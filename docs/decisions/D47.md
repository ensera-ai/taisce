# D47 — A process is not ready on a schema older than the one it was built for

**Date.** 2026-11-11. **Issue.** [#213](https://github.com/ensera-ai/taisce/issues/213).

**Why it was open.** An upgrade starts new processes and the migration at the same moment, and nothing
orders the two. Readiness asked whether the tables a process needs exist, and they do before the
migration as well as after. So a new process that reached the database first reported ready and
served against a schema missing whatever its own release had added, each request failing in its own
way for as long as the migration took. Shown against a real database: with every migration but the
newest applied, the check a process uses to decide it is ready passed.

#213 asks a larger question — what an upgrade promises — and that is still open. This entry settles
only the part that needs no promise.

**Decided.**
- **Every role's readiness first compares the schema's recorded version with the newest migration
  the binary carries.** Lower, or no record at all, is not ready. The API, the worker and the
  management surface all ask.
- **It waits rather than exits.** Readiness is asked on every probe, so a process that started early
  becomes ready on its own when the migration commits. Nothing restarts and nothing has to be
  sequenced by the deployment.
- **It says both versions and what it is waiting for**, because the reader is an operator watching a
  pod not become ready and deciding whether to worry.
- **It is one-sided.** A schema *newer* than the binary is not refused.

**Rejected: refusing a newer schema as well.** It is the symmetrical rule and it closes the other
half of the window: a process from the previous release serving after the migration. Whether that
process is safe depends on what a migration may change between releases. If migrations only ever
add, it is safe and refusing it would take every old process out of service at the instant the
migration commits — before the new ones have been probed — so every upgrade would have a moment with
nothing ready. If migrations may remove, it is unsafe and should be refused. That is the decision
#213 exists to take, and guessing it here would either cause an outage on every upgrade or bless an
assumption nobody made.

**Rejected: exiting when the schema is behind.** The orchestrator restarts the process, which works.
It also turns an ordinary upgrade into a pod in a crash loop with a growing back-off, which reads as
a failure and delays readiness after the migration has landed.

**Rejected: ordering the two in the chart**, with a hook or an init container that waits for the
migration. It fixes the chart and nothing else: the compose file, and anybody running the binary
another way, would keep the race. A property of the binary is held wherever the binary runs.

**Undo cost.** Low. One query in the readiness path and one function. Removing it restores the race
and nothing else.

**Impact.** Operations: an upgrade no longer has a window in which a new process serves errors while
the migration runs. What it does not cover — a process from the previous release still serves after
the migration, on a schema newer than it expects; a migration that fails leaves the new processes
unready indefinitely, which is the correct state and needs an operator; and a rollback to an older
binary is, to this check, a newer schema and is not refused. Performance: one indexed read of a
table with one row per migration, inside the readiness check's existing one-second cache. No figure
is claimed.
