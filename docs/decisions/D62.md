# D62 — A sealed range leaves the ledger for a file under a checkpoint, and nothing else leaves it

**Date.** 2026-11-13. **Issue.** [#250](https://github.com/ensera-ai/taisce/issues/250).

**Why it was open.** The ledger refused every `UPDATE` and `DELETE` from every identity, had no
retention, and was verified by recomputing its chain from the first seal. So it grew with traffic
for as long as the instance lived, and the cost of checking it grew with it. Counting freshness
reads (D56) lowered the slope and left the shape. The only way an operator could make room was to
disable the triggers as the owner: the one act the ledger exists to make visible, done invisibly.

**What is protected, and from whom.** That an act stays on the record, and that the record can be
shown not to have been rewritten — from an operator with database access, and from the process that
serves traffic. A bound must not weaken either: an entry that leaves the table has to remain as
checkable as one that stayed.

**Decided.**
- **A range may leave once it is sealed, as a file.** `taisce audit archive --older-than … --out …`
  writes every seal older than the cutoff and the entries it covers, verifying each seal against its
  entries and its predecessor as it writes. A ledger that does not verify is not archived.
- **It leaves a checkpoint.** The seal the range ran through, the chain's digest there, how much
  left, and the digest of the file. The next seal chains to the checkpoint, and verification starts
  from it, so what remains verifies to the same head and at a cost that follows the ledger's size
  and not the instance's age.
- **The order is: written, durable, named, then removed.** The file exists under its final name
  before the one transaction that writes the checkpoint, removes the range and records the act. No
  failure leaves an entry in neither place.
- **The rules are in the schema.** A delete is permitted only for a row a checkpoint covers. A
  checkpoint names a seal the ledger holds, by its digest, and runs forward; it is never changed.
  The memory role holds no privilege to write one or to delete an entry.
- **A file is checked with no database.** Each entry is stored as the exact line its seal digested,
  so `taisce audit verify-archive` is SHA-256 over lines, compared at the end with a digest from
  outside: the head the worker logged when the range was sealed, or the start of the next archive.
- **The bound is stated as arithmetic on a measured size.** One entry takes about 261 bytes with its
  indexes (PostgreSQL 18.6, 2026-11-13). The ledger holds what was written inside the window plus
  what was written since the archive last ran.

**Rejected, for now: partitioning the ledger by time and detaching sealed partitions.** It was the
option first proposed, and it has one real advantage: a detached partition returns its disk to the
operating system and costs nothing to remove, where deleted rows free space only for reuse and are
removed one by one. Against that: the ledger would have to be rebuilt as a partitioned table by a
migration that copies every row of the one table whose integrity is the point; its key would have
to gain the partition column; seals are ranges of identifiers and not of time, so a seal would
straddle partitions unless sealing learned about them; and partitions would have to be created
ahead of time by something that then must not fail. None of that buys the bound, which a range
delete under a checkpoint already gives. What it buys is cheaper removal and returned disk, and
nothing here has measured removal as a cost. The checkpoint, the file format and verification from
a checkpoint are what partitioning would also need, so this is the first half of that design and
not a different one. Reopen it with a measured removal time or a measured bloat that matters.

**Rejected: leaving it unbounded and documenting the growth.** It is honest and it leaves the
operator's only remedy as the invisible one.

**Rejected: a retention period after which entries are simply deleted.** A record that expires is a
record of the recent past. An act a year old is the one most likely to be asked about.

**Rejected: archiving on a schedule inside the worker.** The worker has nowhere to put a file that
is the operator's to keep, and a process that both serves traffic and removes ledger entries is the
arrangement the grants exist to prevent. It is an operator's command, on the ledger, to schedule.

**Rejected: an archive of separate fields.** A verifier would have to write a number and a time the
way PostgreSQL does before it could hash them. One that must reproduce the database's formatting is
not independent of the database.

**Rejected: writing the checkpoint first and exporting afterwards.** It is the order in which a
crash loses a range.

**What it does not cover.**
- **The file.** The database cannot see it. An archive that is discarded has discarded those
  entries, and the checkpoint then names a file nobody holds.
- **An owner.** As before, an owner can set the triggers aside. An owner can also write a checkpoint
  for a sealed range by hand and delete it without exporting. The seal digests in the process log
  still say what the chain was; the entries are gone.
- **Disk returned to the operating system.** The table stops growing; it does not shrink.
- **Reads of the past.** The console's activity, `LastActed` and the ledger pages read the ledger as
  it stands. What was archived is in files.
- **Time.** Nothing here measures how long an archive takes or how long appends wait while a large
  range is removed. Those need hardware that can be held still ([#155](https://github.com/ensera-ai/taisce/issues/155)).

**Proof.** Against a real database:
- `TestASealedRangeLeavesTheLedgerUnderACheckpointAndTheChainStillVerifies` — two seals leave, the
  file verifies alone against the head from sealing, the ledger verifies to the same head from the
  checkpoint, the next seal chains to it, an uncovered entry still cannot be deleted, and a second
  range follows the first.
- `TestACheckpointCoversOnlyWhatIsSealedAndOnlyAnOperatorWritesOne` — five checkpoints that name
  something other than a real seal are refused; the memory role is refused a checkpoint and a
  delete; a checkpoint is not updated, deleted, truncated or repeated.
- `TestALedgerThatDoesNotVerifyIsNotArchived` — an entry altered as the owner stops the export.
- `TestAnOperatorArchivesASealedRangeAndAnybodyCanCheckTheFile` — the two commands, with the
  database taken away before the file is checked.
- `TestAnArchivedRangeVerifiesAgainstADigestFromOutsideAndNothingElse`,
  `TestEveryWayAnArchivedRangeCanBeAlteredIsNamed`,
  `TestAFileThatIsNotAnArchiveIsAnErrorAndNotAVerdict` — the file.
- `TestALedgerEntryTakesTheBytesItsBoundIsStatedIn` — the size the bound is stated in.

Provoked before kept: a seal after the checkpoint that chained to zero, a verification that started
from the first seal, and a trigger that let an uncovered entry leave. Each failed the first test.

**Undo cost.** The schema change is additive — a table, two functions, two triggers replaced by
ones that behave identically until a checkpoint exists — and is one migration to reverse on an
instance that has never archived. Once a range has left, it is not reversible in the database: the
entries are in files, and the chain starts at a checkpoint for good. The file format is the part
that lasts longest, which is why it carries a version.

**Impact.**
- *Operations.* The ledger has a size an operator chooses, and a command to schedule. Archives are
  a new thing to keep.
- *Security.* The sanctioned way to make room is now on the ledger, where the unsanctioned way never
  was. A new way to lose entries exists — discarding a file — and is stated.
- *Performance.* Verification reads what the ledger holds and not everything it ever held. Nothing
  on the read path changed.
