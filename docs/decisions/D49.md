# D49 — Every pod of a release refuses connections nobody named

**Date.** 2026-11-12. **Issue.** [#222](https://github.com/ensera-ai/taisce/issues/222).

**Why it was open.** The chart rendered no NetworkPolicy. The management surface was described as
unpublished, and at the cluster's edge that was true; inside the cluster every pod in every namespace
could open a connection to it, to the memory API and to PostgreSQL. A token or a password still stood
in the way, so this was never an open door. It was a surface whose only lock is a bearer token,
reachable by any workload that was compromised or was never meant to be a neighbour.

**What is protected, and from whom.** The database, which holds every project's memory and the
credential registry, and the management surface, which holds the connection that can mint a
credential for any project. From a workload elsewhere in the cluster. The worst path is the one this
removes: a foothold in an unrelated namespace becoming a place to guess credentials from.

**Decided.**
- **The chart renders policies, and they are on by default.** One closes every pod of the release to
  all incoming connections. One more per door names who may come through it.
- **The closing policy selects by release, not by component.** A workload added to the chart later is
  closed before anybody writes a policy for it.
- **The memory API admits the pods of its own namespace** on its one port, and whoever else the
  operator names in `networkPolicy.api.from`.
- **The management surface admits nobody until somebody is named.** An operator reaches it through
  the cluster's own API — `kubectl exec`, `kubectl port-forward` — which no NetworkPolicy governs.
- **The database admits three callers:** this release's pods on 5432; its own instances on 5432 and
  the status port, because a replica streams from the primary and a joining instance clones it; and
  the operator's namespace on the status port, because a database the operator cannot see is one
  nobody is failing over.
- **An empty list of callers renders no rule.** In this API a rule with no `from` matches every
  source, so a list emptied to close a door would open it to the cluster, in a valid object, with
  nothing failing. Absence is read as nobody.
- **An ingress whose controller is admitted nowhere is refused at render.** It would otherwise
  install, resolve, and time out on every request.

**Rejected: denying everything in the namespace.** It is the usual shape and the stronger statement.
A chart does not own its namespace: an operator who installs beside something else would have that
something closed by a release that knows nothing about it, and would find out from an outage. The
policies select what this release created and the database it asked for, and nothing else.

**Rejected: restricting what the pods may call.** The API and the workers call a model endpoint the
operator chose, by name, often outside the cluster. A NetworkPolicy matches addresses, not names. An
egress rule written here would be either wide enough to mean nothing or exact enough to break the
first deployment whose endpoint moved; the policies that match names belong to particular network
plugins, and requiring one would make the plugin a dependency. What a model call may reach is bounded
in the binary, by the inference allowlist, where the name is known.

**Rejected: naming the operator by pod label as well as namespace.** It is narrower. The label is the
operator's packaging to change, and a selector that stopped matching would not fail an install — it
would leave a database that is running and that nobody is managing. The operator's namespace is
already a place trusted with every database in the cluster.

**Rejected: off by default, documented.** An operator who has not read the page gets the same
deployment as before, which is the deployment the finding was about.

**Rejected: an address check in the binary.** It is a rule each listener has to remember, it cannot
cover the database, and it sees a connection only after accepting it.

**What it does not cover.**
- **A cluster whose network plugin enforces no NetworkPolicy** accepts the objects and admits
  everybody. Neither a rendering nor an install can tell; only a refused connection can.
- **Anything arriving through the cluster's API**, which is governed by the cluster's access rules.
- **Egress**, as above.
- **Who answers the database's address.** The connection strings still encrypt without verifying;
  that is [#240](https://github.com/ensera-ai/taisce/issues/240), which found that verifying against
  the database's own authority as the pool does today would stop connecting ninety days after a
  process started.
- **A scraper of the database's own metrics port.** The chart configures none, so none is admitted;
  an operator who adds one adds a policy for it. Policies only ever add.

**Proof.** `deploy/helm/networkpolicy_test.go` holds the rendering.
[`docs/37`](../37-helm-cluster-install.md#the-network-policy-meets-a-cluster--2026-11-12) records the
run on a cluster that enforces policy: a two-instance database came up and replicated across two
nodes through the policy, a stranger was refused at every port, and with the policies removed the
same probes connected.

**Undo cost.** Low for a deployment: `networkPolicy.enabled=false` removes the objects on the next
upgrade and no data is touched. The default is the costly part to change later, in one direction —
turning it off again would silently reopen every deployment that relied on it.

**Impact.**
- *Security.* A connection to the database or the management surface from outside the release is
  refused before either process sees it.
- *Operations.* An upgrade to a release carrying this changes who can reach a running deployment. A
  gateway or ingress controller in its own namespace, set up outside the chart, is a stranger until
  `networkPolicy.api.from` — and `networkPolicy.manage.from`, if it routes to the portal — names it.
  The chart can refuse an unreachable ingress of its own; it cannot see a route it did not render.
