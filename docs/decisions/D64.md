# D64 — The schema says how old a binary may be, and a binary older than that stands down

**Date.** 2026-11-13. **Issue.** [#257](https://github.com/ensera-ai/taisce/issues/257).

**Why it was open.** An upgrade is promised one release at a time (D58), and a check holds every
migration to the previous release. Nothing was promised about a process two or more releases old,
and nothing stopped one. An operator who upgrades across two releases in one step leaves processes
of the old release serving, until the roll replaces them, on a schema only ever checked against the
release in between. Readiness did not help: it is one-sided on purpose, because a schema newer than
a binary is the ordinary state of every upgrade.

**What is protected, and from whom.** Callers, from an operator doing something reasonable that the
documentation says not to. "One release at a time" was a rule every operator had to remember.

**Decided.**
- **The schema records the oldest schema version a binary may have been built for and still
  serve**: `schema_serves.oldest_binary`, the newest migration the previous release carries. It is
  written after the migrations by whoever ran them, and only rises.
- **A binary compares the version it was built for with that number on the readiness check it
  already runs.** Built for less, it reports not ready and says so once in its log. The previous
  release is at the number and not below it, so the roll of an ordinary upgrade is unchanged.
- **The number is a file the build checks.** `internal/migrate/oldest-served` moves with every
  release, and a test reads the previous release's tag and fails when the file does not name that
  release's schema. The first change after a release cannot merge without moving it.

**Rejected: the chart refuses the upgrade.** The bootstrap Job could compare the release it is
upgrading from with the one it carries and fail before migrating. It covers the chart and nothing
else — not the compose file, not an operator running the binary — which is why readiness was put in
the binary in the first place.

**Rejected: readiness refuses any schema newer than the binary.** It is the simple symmetrical rule,
and it takes every old process out of service the moment a migration commits, before a new one has
been probed: a moment with nothing ready on every upgrade.

**Rejected: the number in a migration.** A released migration is never edited and this moves every
release, so it would be a new migration per release whose only content is a number — and still one
somebody has to remember to write.

**Rejected: leaving it documented.** The present position, and a rule held by memory.

**What it does not cover.**
- **A binary that does not carry the comparison.** A release older than the one that introduced it
  never looks. It protects upgrades from that release onwards.
- **The gap it creates on purpose.** In a skipped-release upgrade the old processes stand down when
  the migration commits and the new ones become ready after it. Between the two, nothing may be
  ready. That is the honest form of what was happening anyway: requests failing one by one.
- **The control namespace.** The number is about the memory schema, which is what a serving process
  reads.

**Proof.** `TestABinaryTwoReleasesOldIsNotReadyAndThePreviousOneIs` — this release and the previous
one are ready, a binary built for one version less is not, a binary newer than the schema still
waits, and migrating again does not lower the number. `TestTheOldestBinaryServedIsThePreviousReleases`
— provoked with the file set one too low: *says 77, and the previous release, v0.7.1, was built for
schema version 78*. `TestAProcessMoreThanOneReleaseBehindSaysSoOnce` — the log line.

**Undo cost.** Low. One table of one row, one comparison, one file. Removing it returns to the
documented rule.

**Impact.**
- *Operations.* A skipped-release upgrade drains the old processes instead of failing their
  requests. A release now has one more thing to move, and the build refuses to let it be forgotten.
