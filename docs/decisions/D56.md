# D56 — A ledger row is one act, except a freshness read, which is counted

**Date.** 2026-11-12. **Issue.** [#220](https://github.com/ensera-ai/taisce/issues/220).

**Why it was open.** Every operation appended a row to the audit ledger before answering, and a row
can never be removed. That is right for an erasure and expensive for a read. A freshness read wrote
a row; an agent polling once a second wrote 86,400 a day and read nothing but two offsets it was
entitled to. The read path was a write path, and the largest table in a busy instance was the one
that holds no memory.

The question underneath was what a row is: always one act, or one act except reads the caller was
entitled to, which are counted. The owner chose the second on 2026-11-12.

**Decided.**
- **A freshness read is counted, not listed.** The first by a credential in a minute is a row,
  written at once. The rest of that minute are one more row, written when the minute closes, whose
  magnitude is how many there were.
- **Only freshness.** Every write, erasure, export, recall and refusal is still a row of its own,
  written before the caller is answered.
- **Counts of operations read a freshness row as the reads it stands for.** One expression says
  how many operations a row is, and the activity window, its buckets and the per-project ranking all
  go through it — so the ops centre and `taisce_operations_allowed` report what happened.
- **Counts of the ledger as a ledger still count rows**: what a seal covers, what is unsealed.
- **A freshness row from before this has a magnitude of zero and is read as one.**
- **A serving process that is told to stop writes the counts it holds** before its pool closes.

**Why the first read is written at once.** The credential list says when each credential last
appears in the ledger (D50), and an operator reads that before revoking. A credential that only
polls is in use because of exactly these rows. Writing the count alone, at the end of the minute,
would show a credential that has just started as unused.

**Rejected: a row is always one act.** It is the simplest rule and it is what the ledger's name
promises. Its cost is paid by every caller on the path this project protects, for a record of
something that changed nothing and disclosed nothing the caller did not already hold, and it makes
the table that must never shrink grow with polling rather than with anything that happened.

**Rejected: counting other reads as well** — the inspection reads, recall. A recall discloses
memory, and "which credential read, and when" is the record a person asking about their data is
owed. The inspection reads are an operator's or an application's deliberate look, not a poll.
Freshness is the one read that is both entitlement-only and built to be repeated.

**Rejected: writing the row after answering.** It takes the commit out of the caller's wait and
keeps one row per read, so the table grows exactly as before.

**Rejected: one row per window, written when it closes.** It is one row where this writes two. It
makes a credential invisible for up to a minute after it first acts, which is the moment an
operator deciding what to revoke most needs to see it.

**Rejected: updating the first row's magnitude as reads arrive.** The ledger refuses updates, by
trigger, for every identity. That refusal is the ledger.

**Rejected: a function in the schema for how many operations a row is.** It would be one definition
for any reader, including a hand-written query. It is a migration for a rule only this code's
counts apply, and a hand-written query over the ledger is reading rows, which is what it gets.

**What it does not cover.**
- **A bound on the ledger's size.** This lowers the slope; it does not stop the table growing.
  Bounding it means sealed ranges leaving the table — partitioning by time, archiving a sealed
  partition with its seal — and verification that does not recompute the chain from the start. That
  is [#250](https://github.com/ensera-ai/taisce/issues/250).
- **Reads from a replica.** A recall still writes a row, so it still needs the primary.
- **A crash.** A process that dies loses the count of the minute it was in. The first read of that
  minute is on the ledger; the number that followed is not.
- **The count's timestamp.** It is stamped when the minute closes, up to a minute after the reads.
- **Several replicas.** Each counts for itself: a credential polling through two is two first-rows
  and two counts a minute.
- **Refused authentication**, which has always been sampled into rows and counted by row. What that
  number means is unchanged.

**Proof.** `TestAPollerIsTwoLedgerRowsAWindowAndEveryReadIsStillCounted`: fifty freshness reads are
one row at once and the credential is on the ledger; the window closes and a second row carries
forty-nine; the activity total, its buckets and the project's rank each say fifty-three for the
fifty-three reads two credentials made; a row from before is read as one; three recalls are three
rows. With the counts reading rows instead, it fails: `counts 4 freshness reads; 53 were made`.
`TestAWindowThatEndedBeforeItWasClosedKeepsItsCount` holds the boundary between two windows.

**Undo cost.** Low to switch off: a server wired without the counter lists every read again. What
cannot be undone is the detail not kept — the times of the reads inside a counted minute were never
written.

**Impact.**
- *Performance.* After a credential's first freshness read in a minute, a read writes nothing: no
  insert, no commit. No figure is claimed for what that is worth.
- *Operations.* A credential polling once a second is two ledger rows a minute per serving process
  where it was sixty.
- *Security.* The record of who read freshness, and that they did, is kept. When each individual
  poll happened inside a minute is not.
