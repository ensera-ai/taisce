# D66 — Which facts a walk takes at a busy entity stays an arbitrary order until a measurement beats recency

**Date.** 2026-11-13. **Issue.** [#156](https://github.com/ensera-ai/taisce/issues/156).

**Why it was open.** Each hop of the walk takes at most 64 of an entity's facts on each side, in
the order of the fact identifier. The identifier is a hash of the claim, so at an entity with more
facts than the cap the 64 that are taken are the 64 that hashed low: not the newest, not the most
attested, not the most relevant. The bundle says when that cut happened. It does not make the cut
a good one. The question was whether to replace the order with a computed, stored, indexed number.

**What the order must not cost.** Whatever the order is, each side of a hop stays one index seek
that stops at the cap (D63). An order computed over an entity's whole neighbourhood at read time
makes the cost of a recall a property of the busiest entity, which is the curve this design exists
to avoid.

**Decided.**
- **The order stays the fact identifier for now.** It is arbitrary and it is stable: the same
  question returns the same bundle, and nothing claims the 64 are the best 64.
- **A stored salience is not adopted without a measurement, and the measurement has a baseline it
  must beat.** A salience column was dropped once for having no reader, with the condition that it
  return only with the measurement that justifies it. That condition stands, and is made exact:
  salience is adopted only if, on questions about an entity with more facts than the cap, it puts
  more of the facts that answer the question into the bundle than **recency alone** does — the newest
  facts first, one signal, no new column — and than the present order does.
- **If recency alone wins, recency is the order** and salience stays out. That is a different
  `ORDER BY` and two indexes with a different last column, not a ranking stage.
- **Either change keeps the bounded seek**, held by the tests that hold it now.

**Rejected: adopt salience now, from signals already held** — recency, evidence count, the
extractor's confidence, entity degree, recorded feedback. Five signals and a way of combining them,
with nothing to say whether the combination beats its simplest member. It would be machinery with
no reader for a second time, and afterwards nobody could say which signal was doing the work.

**Rejected: switch to recency now, unmeasured.** It is the most defensible single change: newest
first is an order a reader can explain, and the present one is not. It is still a change to what
every recall at a busy entity returns, made on an argument. The walk's indexes are ordered by the
same key as the walk, so it is also a migration, and one that would be made twice if the
measurement then chose salience. It waits for the same run.

**Rejected: rank at read time in SQL.** Described above; it gives up the bound.

**Rejected: a model reranker on the read path.** A model call paid by every caller, producing an
order nobody can explain. It is a different question, and never a default.

**Rejected: a larger cap.** It moves the point at which the question arises and multiplies the work
of every hop below it.

**What it does not cover.** Entities with fewer facts than the cap are unaffected by any of this:
all their facts are taken, in whatever order. The final order of a bundle is a separate cut, by
hops, relation and identifier, and is not decided here.

**What would reopen it.** The measurement, which does not exist yet
([#282](https://github.com/ensera-ai/taisce/issues/282)). The issue that tracks it says what it has to
isolate.

**Undo cost.** Nothing was changed. Adopting an order later is one migration for the indexes and one
clause in two places.

**Impact.** None on what the system does today. It fixes what a later change must show.
