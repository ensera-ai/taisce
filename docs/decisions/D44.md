# D44 — The instance measures how long things take, as rising totals kept in the database

**Date.** 2026-11-11. **Issue.** [#217](https://github.com/ensera-ai/taisce/issues/217). Amends D32.

**Why it was open.** D32 decided two things in one sentence: no tracing, and "no durations were added
to the read path". The argument given was for the first — a span named now follows a convention with
no release. It did not reach the second, and the cost of having no duration anywhere turned out to be
specific. An operator whose agents felt slow had nothing to look at. A backlog said formation was
behind without saying whether that was a slow model or a deep queue, which call for different
remedies. A request refused for capacity wrote no ledger row, so an instance refusing a third of its
load looked, on the scrape, exactly like an idle one. And a latency target, were one agreed (#155),
could not have been checked on any running instance.

**Decided.**
- **Three things are timed.** A request to a memory operation, from the door to the response, by
  operation. A turn's formation, for turns that formed. And how long a turn waited between being
  stored and being formed, which is what an agent experiences as memory not yet knowing what it was
  told and includes the backlog the formation time does not.
- **One thing is counted that the ledger cannot say:** requests refused for capacity.
- **Each process counts in memory and adds to totals kept in the database**, every ten seconds and
  once more when it stops. The process that times a request is not the one that answers the scrape,
  so the numbers have to live where the management surface can read them. Totals, one row per thing
  measured, because the question — how are durations distributed — needs a dozen integers and a row
  per request would be a second ledger.
- **They are real counters and real histograms.** A total in the database only rises and does not
  restart with a process, so a rate over it is the rate it says it is. D32 made the operation counts
  gauges over a window because a cumulative count there meant a full pass over a table that only
  grows; a counter row has no such cost, so that reasoning does not carry over.
- **Two labels, and only two.** `le`, a bucket edge from a fixed list, and `operation`, from the
  surface's own operation table. D32's rule was that the exposition writer has no label parameter at
  all; it still has none that takes a string a caller chose. The scrape refuses, as a whole, a stored
  measurement named for anything the surface does not declare, and the table refuses a name that
  could be read as label syntax.
- **Milliseconds, as integers.** The file that writes the scrape has no float formatter, on purpose,
  and still has none.
- **The bucket edges are spread on a logarithmic scale and tuned to nothing**, because no target has
  been agreed and edges chosen around a guess would put their resolution where the guess was.

**Rejected: a duration column on each ledger row.** It was the first design, and it is nearly free —
the row is already written for every operation, and the scrape already reads the ledger's window. It
gives a window's counts rather than rising totals, so a monitoring system could not take a rate of
them; it measures only what reaches the ledger, which a capacity refusal does not; and it says
nothing about formation.

**Rejected: a scrape endpoint on every process.** It is what most services do, and it needs no
database write. It puts a port on the memory listener that answers questions about capacity and
backlog to whoever can reach the port agents use, which D32 rejected for the reason it still holds;
and a worker listens on loopback only.

**Rejected: an average.** One sum and one count per operation, no buckets and so no `le` label, which
would have kept D32's no-label rule intact. An average of request times says nothing about the
requests an operator is being asked about, and the label it avoids is a list of integers.

**Rejected: timing inside each handler.** It would leave out the credential lookup and the ledger
write — the parts every request shares and a caller cannot avoid.

**Rejected: writing a total on every request.** Exact, and a row update contended by every request
on the path rule 9 says to protect.

**Undo cost.** Low for the mechanism: one table, one wrapper at the door, three lines in the worker.
Not low for the names — a series somebody has written an alert against cannot be renamed without
breaking their rule — and the bucket edges are fixed in stored rows, so changing them means new
series rather than an edit.

**Impact.** Operations: an instance can be asked whether it is slow, and where. Performance: every
request to a memory operation takes one lock and adds to three integers; every ten seconds each
process writes one statement per operation that saw traffic; a worker writes after each turn it
forms. No figure is claimed for what that costs, and none for what the histograms will show — a
percentile read from them is a measurement of one deployment on its hardware. Security: the scrape
gained two labels and no way for a value from memory to become one; the memory role can write the
totals, so a compromised memory process can falsify its own timings, and nothing is decided from
them. What it does not cover — a scrape is up to ten seconds behind a process, and a killed process
loses up to ten seconds of counts; the lag is measured across two hosts' clocks and is skewed by
however much they disagree; model calls for reports, compaction and embeddings are not timed
separately; and the management surface's own requests are not timed at all
([#234](https://github.com/ensera-ai/taisce/issues/234)).
