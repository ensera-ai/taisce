# D60 — The boundary between projects stays a predicate that something checks, and is not a row-security policy

**Date.** 2026-11-13. **Issue.** [#219](https://github.com/ensera-ai/taisce/issues/219).

**Why it was open.** Projects in one instance are separated by a predicate every statement carries.
A statement that forgets it is valid and reaches every project's rows, and nothing checked that one
had not. The only recorded case against moving the boundary into the database was that one login
serves every project, so a policy keyed on the role would have nothing to tell apart. That is true
of a policy keyed on the role and says nothing of one keyed on a setting the transaction states,
which needs one login only. That option had not been considered.

**What is protected, and from whom.** A project's rows, from a statement that names another project
or none: one written under pressure, or one issued for the holder of a different project's
credential. Not from a process that holds the memory login. That process can state any project under
either design, and the boundary against it is a second instance.

**Decided.**
- **The predicate stays, and every statement is read for it.**
  `TestEveryStatementTiesTheProjectOfEachScopedTableItNames` fails on a reference to a table that
  carries a project where the statement ties the project to nothing. An exception is listed with its
  reason, and where the reason is a fact about the schema the test asks the database whether it
  holds.
- **No table enables row-level security.** The policy was built on every table that carries a
  project and measured against the statements recall runs. It leaves the current read alone and
  takes the index away from every read of the past.

**What was measured.** PostgreSQL 18.6, 2026-11-13, by
`TestARowSecurityPolicyTakesTheIndexFromAReadOfThePast`: the policy `scope =
current_setting('taisce.project', true)`, enabled and forced on all 51 tables with a `scope` column,
the statements planned as `taisce_data` with the planner left to choose. Rows read are a scan's rows
returned plus the rows its filter discarded.

| Read | Rows read without a policy | With the policy |
|---|---|---|
| Current facts about an entity | `fact` 1, `entity` 5, `observation` 2 | the same, by the same indexes |
| Facts valid at a moment, entity with 5,000 past facts | `fact` 1 | `fact` 5,001 |
| Facts believed at a moment, one fact with 2,000 versions | `fact_history` 1 | `fact_history` 2,000 |

The cause is a rule of the database and not a property of the fixture. On a table with a policy, a
condition may drive an index only if its operator is marked leakproof. Equality on text and on a
uuid is, so a current read keeps every index it had. A range containing a moment is not, and that
condition is how a read of the past finds the version that was valid or believed then. Under the
policy it becomes a filter applied to every candidate row, so the work grows with how much history
an entity or a fact has — and history is what this system exists to keep.

The counts are rows on a fixture. They are not a latency, and no claim about speed is made from
them.

**Rejected: the policy on every table, accepting the cost.** A forgotten predicate would return no
rows where today it returns everybody's. The price is a read of the past whose cost is the length of
the past. Time is one of the four things this system does that a vector store does not, and the
price would be paid by exactly the instances that used it most.

**Rejected: the policy on every table except `fact` and `fact_history`.** Forty-nine tables would be
bounded by the database and the two that hold the facts would not. It costs everything the full
policy costs outside the plans — a setting stated in every transaction, a transaction around each of
the ninety places the store issues a statement without one, a per-project setting in the worker and in
every operation that spans projects — and the page describing it would have to say the boundary is
in the database except for the facts. A guarantee is relied on at its stated width.

**Rejected: storing the bounds of a range as two plain columns, so that a read of the past uses
leakproof comparisons.** The exclusion constraints that keep one version current are written on
ranges, and a b-tree on a lower bound answers "began before this moment", which still reads every
earlier version. It rewrites the temporal core to arrive at a worse index.

**Rejected: marking the range operators leakproof in the operator's database.** It needs a
superuser, it alters built-in catalog entries the next major version replaces, and a managed
PostgreSQL does not permit it. PostgreSQL as it is found is the only dependency.

**Rejected: reading the past through functions that run with the owner's rights and bypass the
policy.** The predicate would move into those functions, where forgetting it is the same defect with
more privilege behind it.

**Rejected: leaving the predicate unchecked.** Its first run found a retention sweep deleting
another project's rows ([#260](https://github.com/ensera-ai/taisce/issues/260)).

**What it does not cover.**
- **The check reads text.** A predicate that is present and names the wrong project passes. A
  statement assembled at run time is judged in pieces or excused by name.
- **It is a check, not a boundary.** A statement that reaches the database without passing through
  this repository's tests — typed by an operator, or issued by a compromised process — is not read
  by anything.
- **Only the statements recall runs were measured under the policy**: the current read, the read of
  what was valid at a moment, and the read of what was believed at a moment. The write path, the
  sweeps and the vector searches were not, because the first loss decided it.

**What would reopen it.** `TestARowSecurityPolicyTakesTheIndexFromAReadOfThePast` failing. It
asserts the loss, so a database in which a range may drive an index under a policy turns it red, and
its message says to reopen this entry. So would a requirement that two projects in one instance be
separated from a statement nobody reviewed, which today is answered by a second instance.

**Undo cost.** Nothing was changed in the schema, so there is nothing to undo. Adopting a policy
later is one migration to add it and one to drop it; the expensive part is the other direction,
stating the project in every transaction the store opens, and that is why it was measured before it
was built.

**Impact.**
- *Security.* The convention is now checked on every build, and the limit of the check is written
  beside it. The boundary between projects is still enforced by the application and not by the
  database.
- *Performance.* None. No statement on the read path changed.
