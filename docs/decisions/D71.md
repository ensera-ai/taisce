# D71 — The record inventory pages the current facts naming one entity, on the indexes the walk already has

**Date.** 2026-11-13. **Issue.** [#295](https://github.com/ensera-ai/taisce/issues/295), part of
[#294](https://github.com/ensera-ai/taisce/issues/294).

**Why it was open.** The facts around one entity could not be listed. The record inventory paged a
whole project and narrowed by data subject only; entity inspection returns identity and no facts.
The one route from an entity to its facts was a recall, and a recall is a sample by design: a walk
stops at 64 relations a hop in an order that carries no judgement, inside a budget. So "what does
this memory hold about this thing" had no complete answer, for an operator or for anybody auditing
what is held about a thing and not about a person. Whether it could have one was an index question
first: what one page costs at an entity with thousands of facts.

**What is protected.** The project boundary: an entity id in a request is a position, never an
authority. And what an erasure promises: a fact whose source was erased is not on any page.

**Decided.**
- **`POST /v1/records/list` takes an optional `entity_id`.** With it, the pages hold every fact
  that holds now and names that entity, as its subject or as its object, each once, in the order
  and with the cursor the listing already has. A request without it, or with it empty, is the
  request it always was and runs the statement it always ran.
- **It lists what holds now and not what stopped.** That is the one difference from the unfiltered
  listing, which reports closed facts with their status. It follows from what is indexed, below.
- **The project, the data subject and retention are applied as the listing applies them.** The
  project is a predicate on each arm and again on the join that reads the page. The data subject
  is the listing's own rule: a registered source of that subject supports the fact. A fact past
  its retention is not returned. An entity of another project and an id nothing has both get an
  empty page, so the answer does not say which it was.
- **A malformed `entity_id` is `400 invalid_record_page`**, the listing's existing refusal. The
  all-zero UUID is malformed: it names nothing, and accepting it would make an absent filter and a
  filter on nothing two spellings a caller could confuse.
- **No migration.** The page reads the two partial indexes that hold an entity's current facts in
  fact_id order, which exist for the walk. Nothing is added to the write path.
- **The statement runs with sorting and bitmap scans switched off for its transaction.** Without
  that the bound is a property of a planner estimate; see the measurement.

**Measured.** 2026-11-13, PostgreSQL 18.6. Rows and buffers are counts and are quoted as counts; no
timing was taken, because a development machine cannot produce one worth quoting. The fixture is
shaped like an instance: two projects, 10,000 entities in each with about twenty facts as subject
and twenty as object, a quarter of them current, 420,000 facts in all. One entity in the first
project is the subject of 5,000 current facts, the object of 5,000 more, and the subject of 5,000
closed ones.

| Read, at the busy entity | Rows of `fact` read to select the page | Buffers to select it | Buffers in all |
|---|---|---|---|
| Current facts, page of 20, first page | 22 | 27 | 111 |
| Current facts, page of 20, from the 7,000th | 22 | 29 | 113 |
| Current facts, page of 100, from the 7,000th, planner left to choose | 1,561 | 191 | 595 |
| The same, sorting and bitmap scans off | 102 | 107 | 511 |
| Every state, page of 20, plan made without knowing the entity | 15,000 | 605 | 669 |
| Every state, page of 20, plan made for this entity | 649, most of them other entities' | 659 | 723 |
| Current facts narrowed to a subject supporting nearly all of them | 22 | 95 | 159 |
| Current facts narrowed to a subject supporting the last 30 of 10,000 | 9,992 | 10,006 | 10,070 |

The plan of the first row, which is the plan of all the bounded ones:

```
Nested Loop
  CTE page
    ->  Limit
          ->  Unique
                ->  Merge Append   Sort Key: fact.fact_id
                      ->  Limit
                            ->  Index Scan using fact_subject_walk_idx on fact
                                  Index Cond: ((subject_entity_id = $5) AND (fact_id > $2))
                                  Filter: ((scope = $1) AND ((retention_until IS NULL) OR (retention_until > now())))
                      ->  Limit
                            ->  Index Scan using fact_object_walk_idx on fact
                                  Index Cond: ((object_entity_id = $5) AND (fact_id > $2))
                                  Filter: ((scope = $1) AND ((retention_until IS NULL) OR (retention_until > now())))
  ->  CTE Scan on page p
  ->  Index Scan using fact_scope_id_uniq on fact f
        Index Cond: ((scope = $1) AND (fact_id = p.fact_id))
```

Three things follow. A page of current facts is a seek that stops at the page: each arm reads at
most the limit and one more, wherever the cursor is. A page of every state is not: nothing keeps a
closed fact by entity in any order, so it reads the entity's whole history, or walks the project
discarding other entities' facts. And the bounded plan is not the only one the planner will choose
for the bounded statement. Near the end of the entity's facts, it estimated that fewer rows
remained than the page asked for, fetched all that remained on one side and sorted them — 1,505
rows where 46 were needed. Its estimate was low by a constant factor because no statistic says how
many of an entity's facts are current. With sorting and bitmap scans off there is no such plan to
choose, and `TestAnEntitysPageReadsAPageAndNotTheEntity` fails if that statement is removed.

A schema that also holds the same order led by the project uses it for the same bound: 102 rows
and 108 buffers for the page of 100.

**Rejected: a recall with a larger budget.** It is the route that existed, and it cannot become an
inventory by being given more room. The walk stops at a fanout so that a busy entity cannot cost
what it holds; raising the fanout until nothing is cut removes that bound on the read path every
question uses, for the benefit of a reader who is not asking a question. And a recall has no
cursor: an answer that was cut says so and cannot be continued.

**Rejected: a dedicated neighbours endpoint** — `entities/facts`, or facts returned inside
`entities/get`. It would be a second inventory of the same rows with its own page shape, cursor,
refusals, audit operation and credential rule, each of which the listing already has and each of
which would then have to be kept equal to the listing's by hand. What it would return is a record
summary; the listing is where record summaries are paged. A filter is the smaller surface and is
additive under the frozen contract.

**Rejected: paging closed facts as well**, so that the filter narrowed the listing and changed
nothing else about it. It is the cleaner meaning and it has a price on every write. It needs two
more indexes over every version of every fact — `(scope, subject_entity_id, fact_id)` and
`(scope, object_entity_id, fact_id)`, not partial. Measured on the fixture: 24 MB each, against
about 7.6 MB for each index that holds current facts only; 12.2 write-ahead records for a fact written
against 10.2, and 11.1 for a fact closed against 9.1 — about a fifth more on the path every
observation takes. Nobody has asked for an entity's closed facts by entity: they are on the
unfiltered listing with their status, and each fact's earlier versions are in its history. Named
here so that whoever does ask finds the price already counted.

**Rejected: one statement with `subject = $e OR object = $e`.** Two indexes cannot be read as one
sequence, so the order is lost and every current fact of the entity is fetched and sorted to keep a
page. Two ordered arms merged keep it.

**Rejected: leaving the plan to the planner and stating the tail as a limit.** It was the smaller
change. It makes the bound hold on the fixture it was measured on and depend, everywhere else, on
an estimate known to be wrong in one direction. The setting is local to one transaction, removes
two plan shapes and leaves the choice of index alone.

**Rejected: refusing `entity_id` together with `data_subject_id`.** It would keep every accepted
request bounded by its page, and it would refuse the question "what did this person's sources say
about this thing", which is the one an erasure or an access request asks.

**What it does not cover.**
- Closed facts are not on an entity's page.
- With both filters, a page is not bounded by the page. No index holds a subject's facts by
  entity, so the subject is checked on each fact the seek reads, and the seek reads on until the
  page fills: all of the entity's current facts when the subject supports few of them. It never
  reads closed facts or another entity's. `TestAnEntitysPageNarrowedToADataSubjectCostsTheEntitysCurrentFacts`
  asserts both halves, so a change that removes the limit fails there and is written up.
- Facts past their retention and not yet swept are read past, not skipped by an index.
- How two entities are connected. That is the other half of #294 and is not decided here.

**Undo cost.** Low for the code: one optional request field, one store method, no schema. Not free
for the contract: once a release carries `entity_id`, v1 keeps accepting it. What it means is fixed
with it — a later wish for closed facts by entity is a second optional field, not a change to this
one.

**Impact.**
- *Performance.* A page of an entity's current facts reads at most twice the page and two rows to
  select it, at any entity and any cursor. Nothing on the write path, and nothing on the recall path.
- *Operations.* The two entity-led walk indexes now have a second reader. Removing them is safe
  only where the project-led pair exists, which serves this read as well.
- *Security.* No new boundary. The project and erasure are held by the predicates the listing
  already applies, and tested on the new path by name.
