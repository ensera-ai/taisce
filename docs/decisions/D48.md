# D48 — An observer credential scrapes the instance's numbers and opens nothing else

**Date.** 2026-11-12. **Issue.** [#218](https://github.com/ensera-ai/taisce/issues/218).

**Why it was open.** The scrape is on the management surface, and that surface opened for one kind of
credential: the operator's, which creates and suspends projects, issues and revokes credentials and
seals the ledger. So whatever scraped had to hold it — in a scrape configuration, or a Secret in a
monitoring namespace, readable by whoever administers monitoring. D32 calls the monitoring system a
different trust domain from the operator credential; the configuration that let it scrape put the
operator credential inside it. The credential that can mint a key for any project was held by the
system least likely to be treated as holding one.

**Decided.**
- **A third kind, `observer`.** It names no project, and it resolves at one door: the metrics route.
- **Every other door gives it the answer a stranger gets**: each management operation, the portal and
  each memory route. Held by a test that walks the surface's own operation tables and compares each
  route's answer to an observer with its answer to a token nobody issued, so an operation added later
  is covered the day it is added.
- **The operator credential still scrapes.** An operator may read everything on that surface, and a
  deployment that scraped with one must not stop being monitored by upgrading.
- **It is minted over the administrative connection**, `taisce observer issue <name>`, like the first
  operator credential. Revocation and listing are the ones every credential has.
- **Its access column is `read_only`.** The kind is what bounds it, at the door; the column is stored
  at the least authority the kind could mean, so a row read by something that looks only at access
  does not find `read_write` on a credential issued to scrape.

**Rejected: an access mode on the operator kind.** Fewer kinds. It would be a column every management
route has to remember to read, and a route that forgot would open for a credential issued to scrape.
A kind is checked once, at the door, by the function that decides whether there is a grant at all.

**Rejected: the scrape admitted by network identity.** No token to hold. It puts the boundary in the
cluster's network policy, which the chart does not ship and a compose deployment does not have.

**Rejected: an unauthenticated metrics port.** What most services do. It publishes the deployment's
backlog and capacity to whoever can reach the port, which D32 rejected for the reason it still holds.

**Rejected: issuing observers through the management API as well.** The operator's issue route is
part of the frozen contract, and an observer is minted rarely, by whoever is setting up monitoring.
One path until somebody needs the second.

**Undo cost.** Low. One value in a constraint, one resolve function, one door. Removing the kind
means revoking the observers that exist first, since the constraint would refuse their rows.

**Impact.** Security: a monitoring system no longer has to hold the means to mint a key for any
project. What it does not cover — an observer still learns how far behind the instance is, how much
capacity is left and what generation is costing, which is what a scrape is; the operator credential
still scrapes, so a deployment that keeps giving it to monitoring is no better off; and an observer
never expires, like every other credential here. Operations: one more credential to mint when
monitoring is set up, and the documentation now says which one to give it.
