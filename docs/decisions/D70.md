# D70 — An entity's kind is one of six, and a kind outside them is treated as not given

**Date.** 2026-11-13. **Issue.** [#287](https://github.com/ensera-ai/taisce/issues/287).

**Why it was open.** A model proposing a claim also says what kind of thing each end is. The prompt
asks for one of six — person, organisation, place, time, value, thing — and nothing held it to them.
The reply's two fields were copied onto the claim as written, an empty object kind fell back to the
one its relation declares, and a non-empty one was kept whatever it said. Storage wrote it to
`entity.entity_type`, a text column with a default and no constraint, on the first write only, and
every recall naming the entity returned it as `type`.

So the six were closed where a relation declares its object end, by a check in the schema, and open
where an entity says what it is. That was found by reading the path from the reply to the column, and
then shown: a proposal whose `subject_type` is a sentence addressed to whoever reads it next produced
a claim carrying that sentence, before this change, in
`TestAKindOutsideTheClosedSetIsTreatedAsNotGiven`.

It matters because of how a kind is read. Everything else a model writes is checked against something
it cannot influence — the relation against the vocabulary, the quote against the source — or is
returned as somebody's words with the evidence beside it. A kind is returned as a category. A caller
switches on it and nobody attaches a quote to it, so text arriving there is read with less suspicion
than text anywhere else in the answer, and it stays on the entity for as long as the entity exists.

**Decided.** The six are a set in `domain`, spelled exactly as the schema spells them, and `extract`
judges both ends against it. A subject kind outside the set is dropped, so storage gives the entity
the kind it gives any entity nobody typed. An object kind outside the set is replaced by what the
relation declares, exactly as an empty one already was. The claim itself is kept.

A test holds the set in memory to the constraint in the schema, read back from the catalogue, so a
seventh kind added in one place and not the other fails
(`TestTheKindsExtractionAdmitsAreTheKindsTheSchemaAdmits`).

**What this does not cover.** The column. `extract` is the package every proposal passes through, so
the path from a model to storage is closed, and that is a bound in code: a write path added later, or
a statement run by somebody holding the administrative connection, can still put anything there.
Closing the column needs a migration the previous release can serve on (D58), and rows written
before today hold whatever the deployed model produced. Both are
[#289](https://github.com/ensera-ai/taisce/issues/289). Nor does it correct a kind that is one of the
six and wrong: the first write still wins.

How often a live model writes a kind outside the six has not been measured. Nothing in this
repository records what the supported models put in that field, so this entry claims the bound and
not a rate.

**Rejected: refusing the claim.** A refusal is counted and visible, which is its appeal. But the
kind is not what makes a claim a fact — the relation and the quote are — so a model that mislabels
one field would cost a deployment facts it holds the evidence for, and the operator's refusal summary
would fill with a reason they can do nothing about. The extraction rules refuse a claim when what it
asserts cannot be trusted, and a wrong label on a sound claim is not that.

**Rejected: folding case and spelling, so `Person` and `organization` count.** It is what a reader
expects a lenient parser to do. The schema's check on the same set refuses both, and a more forgiving
rule here would be two definitions of one set, with the parity test unable to say which is right. If
a measurement shows a supported model writing a variant often enough to matter, the place to accept
it is the reply parser, as a stated mapping with that measurement beside it.

**Rejected: a schema-enforced enum in the model's reply format.** Where a provider supports it, the
reply could be constrained to the six before it is ever parsed. That asks the provider to hold the
bound, it differs by provider behind an interface chosen for being common to all of them, and a bound
that depends on which endpoint the operator configured is not one the write path can rely on. It can
be added as a second layer; it cannot be the first.

**Rejected: waiting for the column constraint and doing both at once.** The migration has a
compatibility question the code bound does not, and holding the bound for it leaves every turn formed
in the meantime able to write a kind nobody can remove without that same migration.

**Undo cost.** Low for the rule: it is a few lines in one package, and removing them restores the
previous behaviour. What is not recoverable is a kind dropped while the rule is in force — the
model's string is not kept anywhere — which is the intended effect and also the reason folding
variants was weighed before it was rejected.

**Impact.** Security: text a conversation can steer no longer reaches a field that is read as a
category and outlives the conversation. It adds one comparison per end of a proposal on the write
path and nothing on the read path.
