# D67 — A question is anchored by exact name first, and a fused lexical arm is not adopted without a measurement

**Date.** 2026-11-13. **Issue.** [#157](https://github.com/ensera-ai/taisce/issues/157).

**Why it was open.** A question is anchored by an exact probe on an entity's normalised name, and
the semantic anchors run only when that probe found nothing. Three consequences reach an ordinary
question. One that anchors weakly on one name never gets the better semantic anchor, because the
exact probe "succeeded". A misspelling, an inflection or a different word order misses entirely.
And stored spellings do not help, because every spelling of a name normalises to the one key the
probe already uses. The proposal was to run three arms for every question — exact, lexical over
names, and vector — and fuse them by reciprocal rank.

**What is protected.** Exact precision. A question that names something exactly gets that thing,
through one probe of one unique index, with no model and no extension. It is the current path's
whole strength, and the one property a change here can cost.

**Decided.**
- **Exact name stays the primary path**, and the semantic arm stays a fallback for a question the
  probe found nothing for.
- **A fused hybrid with a lexical arm is not adopted without a measurement**, and the measurement
  has two halves. It must put more of the right anchors in front of questions that name something
  stored imprecisely. And it must **not lower** the result on questions that name something exactly.
  The second half decides it: a gain on imprecise questions bought with a loss on exact ones is
  refused.
- **Whatever is adopted, no arm writes.** An anchor is a place to start a walk, labelled with how
  it was reached. That is the answer to the standing objection to fuzzy matching at read time —
  that it would be an invisible merge of two entities — and it holds only while every arm reads.

**Rejected: adopt the three-arm fusion now.** Reciprocal rank has no weights to tune, which is its
appeal and not evidence. It changes which entity a walk starts at for questions that work today,
adds a trigram extension to the substrate image and an index to every namespace, and runs two more
retrievers on every recall on the read path — one of them a model call — against the best case of a
question that would otherwise have missed.

**Rejected: the lexical arm alone, as a second fallback** — tried only when the exact probe finds
nothing. It is the smallest version and has the least to lose: it cannot change a question the
probe answers. It is the likeliest thing to be adopted, and it still adds an extension and an index
for a gain nobody has counted. It is named here so that the measurement is built to count it
separately.

**Rejected: widening normalisation** — stemming, or folding more than case and spacing into the key.
The key is identity: two names that normalise alike are one entity, for good, on the write path. A
looser key merges entities at formation, where the read-time objection to fuzzy matching is
actually true.

**What it does not cover.** A question that names nothing — "list the security requirements" — is
not an anchoring question and is served by the report and passage surfaces. Nothing here changes
them.

**What would reopen it.** The measurement, which does not exist yet
([#282](https://github.com/ensera-ai/taisce/issues/282)).

**Undo cost.** Nothing was changed. Adopting the lexical arm later is an extension in the substrate
image, one index per namespace and one more statement in the anchor step.

**Impact.** None on what the system does today.
