# D58 — A release's schema is one the previous release can serve on

**Date.** 2026-11-12. **Issue.** [#213](https://github.com/ensera-ai/taisce/issues/213).

**Why it was open.** An upgrade migrates the schema and rolls the processes at the same moment. D47
settled the half that needed no promise: a new process waits for its schema. The other half was left
open on purpose. A process of the previous release goes on serving after the migration commits,
until the roll reaches it, and whether that is safe depends on what a migration is allowed to change
between two releases — which nothing stated. Each release was safe to roll or not according to what
its migrations happened to do.

**Decided.**
- **A release may add to the schema. What it removes, renames or tightens must be something the
  release before it does not rely on.** A removal therefore takes two releases: one stops reading
  the thing, the next drops it.
- **The promise is one release wide.** "The release before" is the newest release tag before the
  commit. An upgrade from one release to the next rolls with both serving; an upgrade that skips a
  release is not promised to.
- **What holds it is the previous release's own suite, run on this tree's migrations.**
  `scripts/upgrade-check.sh` checks that release's source out, replaces its migration directories
  with this tree's, and runs every package of it whose tests open the database. It is the last step
  of `make test`, so the build, the release's gate and `make gate` all run it without naming it.
- **A released migration is never edited or removed**, and the same script refuses it. A database
  that recorded a version never runs the file again, so an edit makes new installs and upgraded ones
  different schemas.
- **Readiness stays one-sided.** A schema newer than the binary is not refused: for the previous
  release that is now the ordinary, checked state of every upgrade.
- **Going back one release needs no restore**, by the same promise read the other way, and with its
  limit: the older release was never tested against rows the newer one wrote. The schema itself
  still only goes forward.

**Rejected: upgrades take an outage.** The chart scales serving to zero, migrates, and scales back.
It is simple and it is honest. It is also paid by every caller on every upgrade, by a deployment the
chart otherwise arranges to survive losing a node, and it makes "upgrade" an event to schedule
rather than a thing to do when a release is out — which is how deployments end up two releases
behind an advisory.

**Rejected: a lint over the SQL of new migrations**, refusing `DROP`, `RENAME` and the like. It is
cheap and runs without a database. It asks the wrong question in both directions: it refuses the
drop of something the previous release had already stopped reading, which is exactly the second
step this rule asks for, and it passes a new `NOT NULL`, a narrower `CHECK` or a trigger that
refuses what the previous release sends — none of which contains a word a lint would look for.
What the previous release needs is whatever it does, and only running it says.

**Rejected: running the previous release's published binary through a journey.** It tests the
artifact an operator actually has, which the source at the tag is only a proxy for. It reaches a
handful of statements where the suite reaches most of them, and what a rolling upgrade breaks is the
statement nobody thought to put in a journey.

**Rejected: a promise two releases wide.** It would let an upgrade skip a release. Everything
removed would then linger a release longer, and the check would run two old suites on every
migration, for a need nobody has stated. The narrower promise can be widened later without breaking
anyone who relied on it; a wider one cannot be narrowed.

**Rejected: refusing a newer schema in readiness, now that there is a rule.** For the previous
release it would take every old process out of service the instant the migration commits, before a
new one has been probed. It is the right shape for a process older than that, and that is
[#257](https://github.com/ensera-ai/taisce/issues/257), not this.

**What it does not cover.**
- **Rows only the new release writes.** The previous release's tests write the previous release's
  data. A value the new release starts writing into a column the old one switches on is seen by no
  test of either. Such a change ships its reader a release before its writer; nothing checks that.
- **What the previous release's suite does not exercise**, the model path among it.
- **A process two or more releases old** (#257).
- **Locks.** A compatible migration that holds a busy table until it commits passes.
- **The published binary.** The check builds the source at the tag, not the image an operator runs.

**Proof.** `TestAMigrationThePreviousReleaseCannotServeOnIsRefused` builds a repository with a
release in it and makes each kind of change after it: nothing, an addition, a removal in each plane,
an edit and a deletion of a released migration, no database, no tag. The removal is refused by the
*release's* test, by name, where the tree's own test would pass anything — which is what shows whose
code ran. `TestTheUpgradeCheckRunsWhereverTheSuiteDoes` holds it in `make test` and holds every job
that runs the suite to a checkout with its tags.
[The migrations page](../postgresql/migrations.md#the-check-run-against-a-real-release--2026-11-12)
records the check run for real: the last release's whole database suite against an added column and
table, and against a rename of a column it reads.

**Undo cost.** In the repository, low: one script, one line of the test target. As a promise, high
and one-directional. Once a release has been upgraded in place on the strength of it, withdrawing it
breaks the operators who believed it, and the only way out is the outage this entry rejected.

**Impact.**
- *Operations.* An upgrade from one release to the next has no window in which a serving process is
  on a schema it cannot use, and going back one release is a redeploy. A removal takes two releases
  to land.
- *Cost of change.* A change that adds a migration runs a second suite in the build — the previous
  release's — so its build takes roughly twice as long. A change that adds none pays a `git diff`.
