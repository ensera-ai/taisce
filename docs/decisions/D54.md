# D54 — An append sends everything after the offset claim as one batch

**Date.** 2026-11-12. **Issue.** [#224](https://github.com/ensera-ai/taisce/issues/224).

**Why it was open.** An append takes the project's watermark row in its first statement and holds
it to commit, so appends to one project are serialised by it. Between the two it sent the
observation, then three statements for every message, then the retention stamp — each a request of
its own, each waiting on the network before the next left. For a turn of 64 messages that is 195
waits with the lock held, and the waits, not the work, were most of the hold.

**Decided.**
- **Everything after the offset claim is one batch**: the observation, the three rows for each
  message, and the retention stamp, in the order they were always written.
- **The offset claim stays a statement of its own.** The observation row carries the offset, and a
  batch cannot carry a value from one reply into the next request.
- **A message's chunk identity is generated in the process**, for that same reason: the two
  statements after a message's own need it. It was a random UUID from the column's default and is a
  random UUID now, as the observation's identity already was.
- **Every reply in the batch is read, in order**, so a refusal is reported against the statement
  that drew it, with the database's own error inside. Callers tell a full backlog, a conflict and a
  serialisation failure apart by that error, as before.
- **No throughput is claimed.** What is held is a count: after the statement that takes the lock,
  an append sends one batch, and that does not depend on the turn's length.

**Rejected: taking the watermark lock last**, so that it is held for the offset claim and the commit
alone. It is the larger gain. The observation row carries the offset and is the row every other row
in the transaction refers to, so it would have to be written without one and filled in afterwards,
or written last behind constraints deferred to make that legal. Either changes what the
transaction's intermediate states are, on the path whose every property has a test written against
the present order. The batch changes how the statements travel and nothing about what they are.

**Rejected: one statement per message, as a chain of data-modifying CTEs.** It would make a message
one statement instead of three. The parts of such a statement share one snapshot and do not see
each other's rows, and the tables here carry triggers written against statements that do. It is a
change to what runs, justified by a number nobody has.

**Rejected: `chunk` referring to the message's text rather than copying it.** It halves what the
store holds of every word. It also touches the passage surface and erasure's registry of derived
rows, and whether the storage matters depends on a corpus size nobody has stated (#155).

**Rejected: waiting for a measurement before changing anything.** The issue allows it. The change
needs no number to be safe — the same statements, in the same order, in the same transaction — and
the thing it removes is counted, not estimated. What does wait for a measurement is any claim about
what it bought.

**What it does not cover.**
- **How much faster an append is, or how many a project now accepts.** That is appends per second
  on hardware that can be held still, published with its conditions, and it is owed under #155.
- **The first time a connection sends the batch** the driver prepares its statements first, which
  is a request more. The count held by the test is what the driver is asked to send.
- **The copy of each message's text** in `chunk`, and the commit, are as they were.

**Proof.** `TestAnAppendHoldsTheProjectsLockForOneStatementAndOneBatchHoweverLongTheTurn` counts the
driver's own requests for turns of 1, 2 and 64 messages: one batch of 2 + 3n statements each, and
the same number of single statements for 64 messages as for one. It also reads back that every
message has its chunk, with the same identity and the same words, and its projection. Against the
previous code it fails with `a turn of 1 messages sent 7 single statements with the lock held`. The
write path's existing tests, unchanged, are what say the rows and the refusals are the same.

**Undo cost.** Low. One function; sending the statements singly again needs no migration, since the
column's default is still there.

**Impact.**
- *Performance.* What is sent under a project's append lock no longer grows with the turn. No
  figure is attached to that.
