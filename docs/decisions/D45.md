# D45 — A worker forms a bounded slice of a project and moves on

**Date.** 2026-11-11. **Issue.** [#215](https://github.com/ensera-ai/taisce/issues/215).

**Why it was open.** The driver walked the projects with a backlog one after another, and the worker
did not come back from a project until that project had nothing left to form. Formation is a model
call per message, so a deep backlog held a worker for a long time, and a project written to as fast
as it formed never emptied and held it indefinitely. Every other project's turns waited behind it,
stored and unformed, with nothing wrong with them; with as many such projects as workers the rest did
not form at all. Shown against a real database with one worker and a model that kept one project
busy: the model was asked about forty-five of that project's turns before either of the two projects
with a single turn each.

**Decided.**
- **A worker attempts at most `TurnsPerScope` turns for a project, then moves to the next.** Eight by
  default. Every project with work is reached in every pass.
- **Attempts are counted, not turns formed.** A project whose every turn fails slowly holds a worker
  just as long as one that succeeds.
- **A pass that stopped at its bound starts the next at once.** Otherwise the bound would be a
  throttle — eight turns per interval however fast the model was — and sharing the worker would have
  been paid for in throughput.
- **Projects are taken oldest wait first**, by their oldest unformed turn, then by name. It used to be
  by name alone, which made the same project first every time.
- **The derived passes still wait for a project's backlog to empty.** Reports and segments are model
  calls, and running them after every slice would write a report per slice for a project that is
  about to change again.
- **Zero means no bound**, which is what a command draining one project by hand wants.

**Rejected: several projects at once inside one worker.** A small pool of goroutines, each holding its
own project's lock. It adds throughput as well as fairness, and it adds a second number to size
against the connection pool and the provider's rate limit. Whether one worker should do more at once
is a throughput question with no target to answer it against (#155). The slice fixes the starvation
without deciding it.

**Rejected: a time slice instead of a count.** It adapts to how long a turn takes, which a count does
not. It also makes a test depend on a clock, and the first turn of a slice can overrun any time bound
by a whole turn budget. A count is exact, and the turn budget already bounds each attempt.

**Rejected: scale workers with projects.** What an operator could already do. It leaves the starvation
in place whenever busy projects outnumber workers, which is not something an operator can see coming.

**Rejected: running the derived passes after every slice.** It would keep a continuously busy
project's reports and notifications current. It would also multiply report and compaction calls by
the number of slices, on the model that formation is already waiting for.

**Undo cost.** Low. One field, one check in the loop, one ordering clause. Setting the field to zero
restores the previous behaviour without a code change.

**Impact.** Operations: a project's formation no longer depends on how busy another project is. What
it does not cover — a project that never empties gets no reports, segments or formed-memory
notifications for as long as that lasts, exactly as before; fairness is per worker, so with fewer
workers than busy projects each project still waits for a slice of every other; and the default of
eight is not measured. Performance: moving on costs one query and a lock against a model call per
message, and a pass no longer ends with a full drain, so the ledger seal, the retention sweep and
notification delivery that share the loop are no longer postponed by a long one. No figure is claimed.
