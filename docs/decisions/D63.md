# D63 — A walk reads one project, and names it by equality

**Date.** 2026-11-13. **Issue.** [#274](https://github.com/ensera-ai/taisce/issues/274).

**Why it was open.** The fanout cap is meant to bound what one hop of the walk reads at a busy
entity: 64 facts, and one more to say it was cut. A test held that on a fixture where one entity
holds most of the facts. On a fixture shaped like an instance — thousands of entities with a few
facts each and one busy one — the current read at the busy entity read 5,000 rows for a cap of 64.

The cause was in how the walk named its project. It took a list, `scope = ANY($1)`, because a
caller was once meant to be able to hold several projects and recall across them. No index can
hand back one order across the several ranges a list on its leading column is, so the indexes that
hold an entity's facts in order led with the entity and checked the project on each row. The
planner cannot know an entity belongs to one project, so it priced that index as fetching the
entity's rows from every project. It does not know which entity a hop is at, so it plans for a
typical one, whose handful of facts cost nothing to sort. It chose an unordered index and a sort.
For a typical entity that was right. For the busy one it read everything.

**What is protected.** The property the read path is built around: what a recall reads at an entity
is bounded by the cap, and not by how busy that entity is.

**Decided.**
- **A walk reads one project.** Named none, it reads nothing. Named several, it is refused
  (`ErrWalkReadsOneProject`). The only caller there is passes the one project its credential names.
- **It names that project by equality**, and two indexes lead with the project, then the entity,
  then the fact identifier (`0081`). With both equalities in the index and the order after them, the
  ordered seek reaches the same rows as any other index and does not sort them, so it is never the
  dearer plan, whatever the planner believes about a typical entity.
- **Reads of the past keep the indexes they had.** What was valid at a moment is found by the
  moment and stops at the cap. What was believed at a moment costs the history of the entity it is
  at, and that is stated and tested as a limit.

**What was measured.** PostgreSQL 18.6, 2026-11-13, rows of `fact` read by one hop at an entity with
5,000 current facts, among 6,000 entities with a few facts each (fixtures of 130,000 and 305,000 facts):

| Statement and index | Rows read |
|---|---|
| Project as a list, entity-led walk index available (before) | 5,000 |
| Project as a list, project-led walk index | 5,000 |
| Project by equality, project-led walk index | 65 |

The middle row is why the index alone was not the fix. Rows on a fixture; no claim about speed.

**Rejected: keeping the list and adding the project-led index.** Measured above: 5,000.

**Rejected: a statement per number of projects** — equality for one, a list for several. It keeps a
capability with no caller and leaves the unbounded plan in the code for the day somebody uses it.

**Rejected: running the walk once per project and merging.** The row limit, the order and the "this
was cut" signal are each defined over one walk. Merging several is a second definition of all
three, for a caller that does not exist.

**Rejected: steering the planner** — a setting for the statement, or writing the project condition
in a form no index can use so that only the entity-led index qualifies. The first needs a
transaction around every recall. The second depends on what the planner cannot do, and the database
under test can already skip a leading column it has no condition for.

**Rejected: leaving it.** The existing test passed, and would have gone on passing.

**What it gives up.** A recall across several projects in one bundle. It was built when a project
was a permission a caller could hold several of. A project is now the unit of content isolation
(D34, D60), a credential names one, and nothing asked for the other.

**What it does not cover.**
- **The role and subject filters** are still checked on each row fetched. An entity whose first
  facts in order are all of a role the caller did not select is read past them until the cap fills.
- **A read of what was believed at a moment** at an entity with a long history reads all of it.
- **The previous release**, which still names its projects as a list. The entity-led indexes stay
  for it for one release and are then removed ([#275](https://github.com/ensera-ai/taisce/issues/275)).
  Until an instance runs this release, its busy entities are read whole.

**Proof.** Against a real database:
- `TestTheFanoutCapBoundsABusyEntityAmongManyQuietOnes` — 65 rows at the busy entity. Provoked: with
  the list restored it fails with *the walk read 5000 rows … the cap is 64*.
- `TestTheFanoutCapBoundsTheRowsAHubEntityIsReadFor` — the earlier shape, still bounded.
- `TestAReadOfThePastReadsItsOwnEntityAndNeverTheInstance` — the reads of the past, both halves.
- `TestARecallReadsTheOneProjectItWasAuthorisedFor` — a second project's facts do not come back, and
  a recall across two is refused.

**Undo cost.** Low in the schema: two indexes to drop. The statement is one predicate in two places.
What does not come back cheaply is the reason the list existed; restoring a recall across projects
means solving the bound again.

**Impact.**
- *Performance.* The work of a hop at a busy entity is the cap and not the entity. Two more indexes
  are maintained on every fact written, beside the two they replace, for one release.
- *Security.* One fewer way for a read to span projects.
