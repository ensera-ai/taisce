# D61 — An erasure leaves a keyed trace in the process log, and a replay applies it again after a restore

**Date.** 2026-11-13. **Issue.** [#228](https://github.com/ensera-ai/taisce/issues/228).

**Why it was open.** A restore returns the database to an earlier moment. Everything erased since
is in it again, and the receipts for those erasures are not, because a receipt is a row in the
database that was just rolled back. The system then holds a person it was told to forget and has no
record of being told. While a backup was something an operator arranged alone this was a caution in
a document. The chart now renders the archive and the schedule, so the path that produces the
restore is this project's own.

**What is protected, and from whom.** The claim that an erasure can be shown to have happened, from
an operator recovering from an incident and doing the right thing. Nobody is hostile in the case
this exists for. The second asset is what the remedy must not create: a list, outside the database,
of the people who asked to be forgotten.

**Decided.**
- **Each erasure writes a trace to the process log.** A line holds the erasure's identifier, the
  project, whether it named a person or a set of turns, and a digest of each identifier it named.
  The log is the one place every deployment already keeps outside the database, so nothing new has
  to be run to hold it.
- **The digest is keyed, and the key lives with the deployment's secrets.** Not in the database,
  where a restore would return it along with what it protects, and not in the log, beside what it
  keys. The chart generates it once, in a secret of its own that the database's secrets do not
  replace. Without the key, a trace says that an erasure happened and how large it was. With it, a
  reader can test an identifier they already know; they cannot list anybody.
- **The trace is written inside the erasure's transaction, before the commit, and its failure is the
  erasure's failure.** The other order leaves a window in which an erasure has committed and has no
  trace, and a restore then undoes it for good. This order leaves a window in which a trace exists
  for an erasure that did not commit — and replaying that erases what its owner asked to have
  erased.
- **`taisce erasure replay` applies again what the restored database has no receipt for.** It
  digests every person or turn the project holds, erases the ones a trace names through the walk
  any erasure takes, and writes the receipt back under the identifier the erasure first had. That
  identifier is what makes a second run do nothing.
- **A replay refuses what it cannot be sure of**: traces written under another key, a trace missing
  one of its lines, a project the database does not have. Each would otherwise be reported as
  "nothing held", which is the answer that ends an operator's search.
- **No key is said, not refused.** A service without a key warns once at start and erases without a
  trace. A key that is set and unusable stops the process.

**Rejected: the application keeps its erasure requests and repeats them.** It needs no new mechanism
here, and it moves the guarantee to every caller: each one would have to keep a durable list of the
people who asked to be forgotten, which is the list this design exists not to create, held by the
party least equipped to protect it. An operator who restores would also depend on every application
team having done so.

**Rejected: writing the trace to a table, or to a second database.** A table is restored with the
rest. A second database is a second thing to run, back up and prove an erasure covered, and
PostgreSQL is the only dependency.

**Rejected: an object store or a destination the operator names.** It is a new dependency and a new
credential on the path of every erasure, to hold a few hundred bytes the log pipeline already
carries.

**Rejected: the identifier, or an unkeyed hash of it, in the log.** The first makes the least
protected store in a deployment the record of who asked to be forgotten. The second is the first
for anybody who can guess: an identifier is commonly an address or a number, and a guess can be
hashed.

**Rejected: writing the trace after the commit.** Described above; it fails in the direction that
cannot be recovered.

**Rejected: refusing to erase when no key is set.** It would trade the act for the record of the
act. An instance that cannot be restored correctly should still be able to forget somebody.

**Rejected: a receipt for an erasure that matched nothing.** A receipt names what it erased, and a
replay that found nobody holds only a digest. "Nothing held" is reported and no row is written; a
second run asks the same question and gets the same answer.

**What it does not cover.**
- **A lost key.** Every trace written under it is unreadable. Nothing detects the loss until a
  replay is needed.
- **A line the log lost or aged out.** That erasure is not repeated. The logs have to be kept at
  least as long as the oldest backup that might be restored, and nothing here checks that they are.
- **A replay run after the instance has gone back to work.** It erases by identifier, so it removes
  what that person has written since the restore as well. Nothing distinguishes someone who never
  came back from someone who did. The order is restore, replay, serve.
- **Removals that are not erasures.** A withdrawn entity, a deleted artifact and a retracted record
  are returned by a restore and are not traced.
- **A restore on a real cluster.** The test returns one namespace's rows on one database. An
  archive, a recovery and the time they take are a drill that has not been run
  ([#267](https://github.com/ensera-ai/taisce/issues/267)).
- **The compose deployment by default.** It ships with no key, because a default written in a file
  is a key everybody holds, and its logs live on the disk that would be restored.

**Proof.** Against a real database:
- `TestAnErasureARestoreUndidIsAppliedAgainFromItsTrace` — a person and a set of fifty-one turns are
  erased, the namespace is put back to before either, and the replay is given the log alone. Both
  are erased again with a residual of zero, both receipts return under their first identifiers, the
  ledger holds an operator's entry for each, a bystander loses nothing, and a second run does
  nothing. Along the way: another key, a trace missing a line, a missing project, a stranger, a
  line that is not a trace.
- `TestAnErasureThatCannotLeaveATraceDoesNotHappen` — a recorder that fails leaves every row and no
  receipt.
- `TestAReplayedErasureComesBackUnderItsOwnIdentifierOnce` — the second replay of one erasure is
  told the database already holds it.
- `TestATraceNamesNobodyToAReaderWithoutTheKey`, `TestATraceIsReadBackWhateverTheLogWrappedAroundIt`,
  `TestATraceThatCannotBeReadIsAnErrorAndNotASkippedLine` — the trace itself.
- `TestTheChartGivesTheRolesThatEraseAndReplayAKeyOfItsOwn` — the role that erases and the role that
  replays hold the key; a worker does not; the reference is not optional.

**Undo cost.** Low for the mechanism: one hook in the eraser, one command, one secret, no schema
change. The format of a line is the part that lasts — lines already in a log store are read by
whatever replays them later — which is why a line carries its version in its marker.

**Impact.**
- *Security.* A restore no longer silently returns an erased person. A new secret exists, and what
  its disclosure gives is stated above.
- *Operations.* A restore has a step after it, and two things to keep that were not kept before: the
  key, outside the cluster, and the API's logs, for as long as the oldest backup.
