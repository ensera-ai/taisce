# D53 — The backlog limits are an operator's setting, a stored turn wakes a worker, and a refusal says how long a turn takes

**Date.** 2026-11-12. **Issue.** [#216](https://github.com/ensera-ai/taisce/issues/216).

**Why it was open.** Past its limit a project accepts writes at the speed a model forms them. Three
things made that harder to live with than it needed to be. The limits were changed by an `UPDATE` in
a database session, with nobody's name on it. A writer at capacity was always told to wait one
second, whatever the instance was doing. And an idle worker looked for work every five seconds, so
a turn stored on a quiet project waited up to that long before anything began.

**Decided — the limits.**
- **They are set on the management surface**, `POST /manage/v1/backlog/limits`, and by
  `taisce backlog limits`, which speaks only that surface.
- **The change is on the ledger**, against the operator, as `backlog.limits`.
- **The bounds stay in the table.** The route passes what it was given and reports the table's
  refusal; there is no second copy of the bounds in code.

**Decided — the wake-up.**
- **A process that stores a turn announces it with a notification; each worker listens.** A woken
  worker runs the pass a tick runs.
- **The tick stays**, so a lost announcement costs a wait and nothing else.
- **The announcement is sent after the write commits, by one goroutine per process, at most once
  every 200 ms.**
- **It carries the schema's name and nothing from memory.**
- **The listening connection comes out of the worker's own pool.**

**Decided — the wait a refusal states.**
- **`Retry-After` is how long the instance currently takes to form one turn**: the time between two
  readings of its formed-turn count, divided by how many formed between them.
- **From 1 to 30 seconds, and 30 when nothing has formed in two minutes.**
- **It is read from the count the workers already write down**, sampled every ten seconds by the
  serving process. Nothing is queried when a write is refused.

**Rejected: announcing inside the write's transaction.** It is the exact mechanism — delivered when
the turn commits, never lost. It puts a statement on every write for something only an idle
instance benefits from; it cannot be bounded, so a bulk ingest sends a wake-up per turn to a worker
that is already awake; and a transaction that has notified commits under a lock PostgreSQL takes
for its notification queue, shared across the database. That last is the database's design as its
source describes it and was *not measured here* — it is a reason to be careful, and the first two
hold whatever it costs.

**Rejected: a shorter tick.** No connection held, no channel. Every worker then queries for work
several times a second for as long as the instance exists, to save a wait that only occurs when it
is idle.

**Rejected: a project's name in the announcement**, so that a worker goes straight to it. Any role
that can log in to the database can listen on any channel. The payload would carry which projects
are being written to, and when, to the registry's role — around the grants that keep it out.

**Rejected: a listening connection opened beside the pool.** It would leave the pool whole. It
would also be a connection the deployment's stated ceiling does not count, on a database whose
ceiling is checked at startup against exactly that statement.

**Rejected: a second copy of the limits' bounds in the route.** It gives a friendlier message per
field. It is also the copy that drifts, and the table refuses the same values either way.

**Rejected: a direct path for the limits over the administrative connection.** It is the
unattributed `UPDATE` this replaces, with a command in front of it.

**Rejected: estimating the wait from the queue's depth.** Depth over rate is how long until the
backlog is *empty*. A refused writer needs room for one turn, which exists as soon as one forms.

**Rejected: querying for the rate when a write is refused.** It would be current to the second. A
refusal is the cheapest thing this service does, and a flood of them is when the database least
needs a query each.

**What it does not cover.**
- **The estimate is the instance's, not a project's.** Workers take projects in turn, so for one
  project it is a floor, low by up to the number of projects with a backlog. No factor is promised.
- **It trails the instance** by up to the ten seconds the count is written on.
- **A turn stored by a process that dies before announcing it** waits for the tick. So does every
  turn while a worker's listening connection is down.
- **A bulk path.** Whether document ingestion needs more than a larger limit is #189's to measure.
- **A limit per project.** The per-project limit is one number for all of them.
- **The chart sets neither limit.** They are changed on a running instance.

**Proof.** `TestATurnStoredOnAnIdleInstanceStartsFormingWithoutWaitingForTheTick`: a turn stored
over the memory API forms with the worker's interval set to an hour; with the write path's mark
removed it fails (`1 pending, 0 wake-ups since it was stored`).
`TestABurstOfWritesIsAFewWakeUpsAndAnotherSchemasWritesAreNone`.
`TestAnOperatorSetsTheBacklogLimitsAndTheLedgerSaysSo`: the limit is the one the write path
enforces on the next write, seven invalid changes change nothing, and the ledger holds the two that
were made. `TestAWriterAtCapacityIsToldHowLongATurnTakesToForm` and
`TestTheRefusalForAFullBacklogCarriesTheEstimate`.

**Undo cost.** Low. The route and the listener are additive; the migration adds one name to the
ledger's list. Removing the announcement returns every turn to the tick.

**Impact.**
- *Operations.* Tuning the backlog is an operator's act with a record. A worker holds one more
  session open, out of the pool it already declared.
- *Performance.* The write path gains a non-blocking channel send. An idle instance starts forming a
  stored turn within the announcement's gap rather than within the tick; no figure is claimed for
  how long that is on a deployment.
