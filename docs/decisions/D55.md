# D55 — A connection to the database verifies who answered, against the authority as it is now

**Date.** 2026-11-12. **Issue.** [#240](https://github.com/ensera-ai/taisce/issues/240).

**Why it was open.** Every connection string the chart built said `sslmode=require`, which encrypts
to whoever answers and checks nothing about them. Verifying was available — the operator publishes
its certificate authority beside the database — and could not simply be switched on: that authority
is valid for ninety days, and a connection pool reads it once. A process running since before a
replacement would verify against the old certificate until it expired, and then refuse every new
connection, on every replica at once, with nothing restarting them.

**What is protected, and from whom.** The connection between a pod and its database, from something
on the path that answers in the database's place. A login can be relayed through such a thing and
everything said afterwards read. The network policy (D49) narrows who can reach the port; it says
nothing about who is behind the address.

**Decided.**
- **A pool reads its certificates again for every connection it opens.** The connection string is
  parsed again, and the TLS settings it yields replace the ones the connection would have used.
- **Both pools do it**: the serving processes' and the one the management surface and the commands
  hold.
- **The chart's connection strings say `verify-full`**, naming the authority's certificate at a
  path each connecting pod mounts.
- **A pod is given one key of the operator's secret, by name.** The same secret holds the key the
  authority signs with.
- **Trust material that cannot be read fails the connection.** It does not fall back to what was
  read earlier, or to no check.

**Rejected: `verify-ca`.** It needs no name to match. The operator's authority signs a certificate
for every database it runs, so checking the authority alone accepts any of them at this address.

**Rejected: reading the authority's file and replacing the pool's roots.** It is less work per
connection than parsing the string. The driver builds each mode's settings differently, and
`verify-ca` as a verification that closes over the authority it was given — replacing the roots
afterwards leaves the old one in force. Parsing again yields what a newly started process would
use, for every mode, and re-reads a client certificate and key as well.

**Rejected: an authority supplied by the chart, valid for years**, handed to the operator to sign
with. It moves the date instead of removing it, and puts a long-lived signing key in a secret this
release owns.

**Rejected: restarting the pods when the secret changes.** It needs something watching the secret,
which this deployment does not have, and it makes a certificate's renewal a rolling restart.

**Rejected: failing liveness when the database cannot be reached**, so that the platform restarts
the pod and the restart re-reads the file. A database that is briefly down would then restart every
pod that depends on it.

**Rejected: mounting the operator's secret whole.** It is one line shorter. Every pod of the release
would then carry the means to mint a certificate for the database.

**What it does not cover.**
- **A connection that is already open** was verified when it was opened and stays as it is.
- **The external mode.** The connection strings are the operator's and so is what they verify. One
  of theirs that names `sslrootcert` is re-read the same way.
- **An operator's database that takes its authority from somewhere other than `<cluster>-ca`.** The
  chart names that secret and exposes no setting for another.
- **The first install waits for the secret.** A pod that mounts it does not start until the operator
  has created the cluster — the wait the pods already had for the database itself.
- **The HTTP listeners.** The memory API and the management surface still serve plain HTTP behind
  whatever terminates TLS in front of them.
- **Other tools that open a connection of their own** — the documentation generator — read their
  certificates once. They run for seconds.

**Proof.** `TestANewConnectionIsVerifiedAgainstTheAuthorityAsItIsNow`: a real database behind real
TLS, both pools built by the constructors a process uses. The authority is replaced under the
running pools and both go on connecting; a pool that reads the file once, on the same connection
string, is refused, which is the defect. Then the replaced authority's certificate is refused, a
certificate for another name is refused, and a missing or unparseable file opens no connection.
With the re-reading removed from the serving pool the test fails at the replacement.
`TestEveryConnectionTheChartBuildsVerifiesWhoAnswered` holds the rendering: every connection string,
the mount in each of the four workloads, and that one key is projected and the signing key is named
nowhere. [`docs/37`](../37-helm-cluster-install.md#the-databases-certificate-is-verified--2026-11-12)
records the authority's ninety days and the chart's mount and connection string run on a cluster.

**Undo cost.** Low. The connection strings are three lines of a template, and the re-reading is one
function both constructors call. Undoing it returns to an unverified connection, not to a broken one.

**Impact.**
- *Security.* A pod no longer sends its login to whatever answers at the database's address.
- *Operations.* An upgrade to a release carrying this needs the image that carries it: the chart
  and the image are released together, and an older image under this chart would stop connecting
  ninety days after its pods started. A pod now refuses to start without the operator's secret.
- *Performance.* A parse and a file read for each physical connection a pool opens, beside a TLS
  handshake; nothing on a request's path.
