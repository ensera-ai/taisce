# D52 — A model call is timed by its purpose and whether it was answered; the management surface by operation

**Date.** 2026-11-12. **Issue.** [#234](https://github.com/ensera-ai/taisce/issues/234).

**Why it was open.** A turn's formation was timed as a whole and a turn makes several model calls,
so a slow turn could not be narrowed to a slow pass, and a slow embedding provider showed only as a
slow recall. The management surface was not timed at all.

**Decided.**
- **Every model call is timed, under the purpose it was made for**: the three generation purposes
  and `embedding`. The set is declared in the inference package, beside the code that makes the
  calls.
- **The clock starts where the request leaves and stops when the caller returns.** A request
  refused before it was sent is not timed, and neither is an embedding answered from the request's
  own memo: neither was a call.
- **Answers and failures are separate series.** *Answered* means a reply arrived with a success
  status and could be decoded.
- **A request to the management surface is timed from the door, by operation**, from that surface's
  own table.
- **The ops centre is timed as a page or an action**, two names.
- **A stored name no set declares fails the scrape**, per family, as it already did for operations.

**Rejected: one series per purpose, failures included.** It is one histogram fewer per purpose. A
refused connection fails in a millisecond and a timeout fails at the client's deadline, and both
are the cases an operator most needs to see. Mixed into the answers, the first makes a failing
provider look fast and the second moves the tail to a number that is the client's setting and not
the model's speed.

**Rejected: counting a reply refused for what it said as a failure.** A reply cut at the ceiling, or
one that does not parse as proposals, took as long as an answer because it was one. How often that
happens is already counted where the refusal is made (D46); timing it as a failure would put
ordinary generation times in the series that is meant to show the provider not answering.

**Rejected: timing the ops centre by route.** It is what a web framework does by default and it
gives the most detail. A project page's path contains the project's name, and a label on a scrape
goes to a system whose access and retention this deployment did not choose. The table that holds
these rows already refuses anything but a declared name for that reason.

**Rejected: timing the scrape.** It is the one management request made on a schedule, so its series
would dominate the family. Whatever scrapes records how long each scrape took, from the side that
waited.

**Rejected: timing the embedding commands that run as their own process.** They hold no writer for
the instance's totals, and what they report is progress, printed as they go.

**What it does not cover.**
- **Time inside the provider is not separated from the network to it.** The clock is this process's.
- **A stand-in provider is what the purpose test calls.** It shows which name each caller times
  itself under and that the clock waits for the reply. That a live provider's calls land in the
  series is shown only where formation runs against one.
- **These are as approximate as every other timing here**: written down every ten seconds, so a
  killed process loses what it counted since.

**Proof.** `TestEachModelCallIsTimedUnderItsOwnPurposeAndNoOther` in the inference package: each
generation pass and the embedding, answered, refused by the provider, cut, unsent, and memoised.
`TestTheScrapeSaysHowLongModelCallsAndTheManagementSurfaceTook`: the published families, that a
project's name from a portal route is absent, and that five undeclared names each fail the scrape.

**Undo cost.** Low. Two kinds in a check constraint and two families on the scrape; removing them
loses history and nothing else.

**Impact.**
- *Operations.* A slow turn is attributable to a pass, a slow recall to the embedding provider, and
  a failing provider is visible as failures rather than as an average.
- *Performance.* Each timed call adds a lock and three integer additions in memory; nothing is
  written on a request's path.
