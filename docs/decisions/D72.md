# D72 — An entity's kind is held to six by the schema: a seventh is stored as a thing, and refused only where nothing stores it as one

**Date.** 2026-11-13. **Issue.** [#289](https://github.com/ensera-ai/taisce/issues/289).

**Why it was open.** D70 held a model's kind to six in `extract`, and said what that left: the
column. `entity.entity_type` was text with a default and no constraint, so the bound held for the
write path that passes through extraction and for no other. There are three statements that write
the column — the entity a claim names, a speaker, and an entity put back from a retained receipt —
and beyond them the previous release, which writes a model's kind as it arrived, and anybody holding
the administrative connection. A receipt carries each end of a fact as the entity was when the
receipt was written, kind included, so a receipt written before D70 holds whatever the model said,
and it is the release holding the bound that restores it.

The obvious answer, a check on the column, is not available bare. The previous release's write of a
seventh kind is a whole turn and a receipt's is a whole restore, and a release's schema is one the
previous release can serve on (D58).

**What is protected.** What a caller reads as a category. A kind comes back on every recall with no
quote beside it, so a caller switches on it and reads it with less suspicion than any other text in
an answer. The actor is whoever can get text into a model's reply; the worst path is that text
arriving in a field read as trusted, and staying on the entity for as long as the entity exists.

**Decided.**
- **A check closes the column**: `entity_kind_chk`, the same six `predicate_object_kind_chk` closes.
- **A trigger in front of it stores a kind outside the six as `thing`**, on insert and on an update
  of the kind, and the write succeeds. That is D70's rule — the claim is sound and the label is not,
  so the label is treated as not given — applied where every writer passes instead of where one
  does. It runs before the check, so the check is never what an ordinary write meets.
- **The check refuses where the trigger is not in the way**: a restore that loads rows before it
  creates triggers, a session with triggers switched off, a table it was disabled on. The role the
  service runs under can do none of those.
- **Rows already written are rewritten by the migration**: an entity whose kind is outside the six
  becomes a `thing`. What it said before is not kept.
- **Retained receipts are not rewritten.** A receipt is the record of what a fact was. The trigger
  meets its kind on the way back in.
- **The trigger stays.** It is not a shim for one release: receipts written before D70 can be
  restored by any later release, and they are the reason.

**Measured.** 2026-11-13, PostgreSQL 18.6; counts, not timings.

- *The write path.* The trigger is guarded by a condition the executor evaluates itself. For 1,000
  entities written with one of the six its function ran 0 times; for 1,000 written with a seventh
  kind, 1,000 times (`TestTheKindTriggerRunsOnlyForAKindOutsideTheSix`). No release from this one on
  writes a seventh kind through extraction, so the cost on the write path is one comparison against
  six strings per entity written.
- *The rewrite, as first written.* One `UPDATE` over 20,000 entities with a kind outside the six
  failed with "out of shared memory". Any update of an entity discards its embedding under a lock
  held until the transaction ends, a migration is one transaction, and a default server's lock
  table holds about 6,400. So the upgrade could not complete on exactly the deployments with the
  most to rewrite.
- *The rewrite, as it is.* With that one trigger off for the statement and on again after it, in
  the same transaction: completes, no such lock taken
  (`TestTheKindBoundAppliesToMoreEntitiesThanTheLockTableHolds`, which fails with that error when
  the two lines are removed). Skipping the discard loses nothing: an embedding is made from an
  entity's name, its spellings and the words said about it, and never from its kind.
- *How many entities a real deployment holds outside the six.* Not measured. No deployment holding
  entities was available to count on this date, so D70's sentence still stands: how often a model
  writes a seventh kind is not known. The count is therefore one an operator takes on their own
  database before upgrading, and the migration states the query.

**Rejected: the check alone.** It is the boundary and nothing else is. It fails a turn of the
previous release whenever a model wrote a seventh kind, and it fails a restore from a receipt that
holds one, in every later release. Both are a fact lost over a label, which D70 already declined.

**Rejected: the trigger alone, and the check a release later.** It was the candidate the issue
named, and it serves the previous release. It leaves the column open wherever a trigger does not
run, which is the case a boundary exists for; and "a release later" has no date once receipts are
counted, because nothing bounds how old a receipt a deployment may restore. With the trigger in
front, the check costs the previous release nothing, so there is no reason to wait.

**Rejected: a trigger that refuses.** A refusal is counted and visible, which is its appeal. It is
the bare check with a better message.

**Rejected: keeping what was written**, in a second column or a table beside the entity. It would
let an operator see what the upgrade changed, and it would answer D70's open question on every
deployment that upgrades. It is also a model's unbounded text, tied to no data subject, in a place
no erasure sweeps — and the reason for the bound is that this text should not be kept where it can
be read as something else.

**Rejected: a count kept by the migration**, with no text. It has no reader after the day of the
upgrade, and the count is available before it from one query.

**Rejected: mapping near misses** — `Person`, `organization`, `company`. D70 rejected it for the
reply and the reasons hold here: two definitions of one set, and a mapping nobody has measured the
need for.

**Rejected: rewriting retained receipts.** It would let the trigger be dropped one day. A receipt
is evidence of what was held, and rewriting evidence to simplify a schema is the wrong trade.

**Rejected: leaving embeddings to be discarded by the rewrite.** It needs no special case in the
migration. It cannot complete past a few thousand entities, and where it could, every rewritten
entity would be embedded again — a model call each — for a change the embedding does not read.

**What it does not cover.**
- A seventh kind written by hand through the ordinary path is not refused. It is stored as a
  `thing`, silently, like any other.
- Nothing counts how often the trigger fires.
- A kind that is one of the six and wrong. The first write still wins.
- What an upgrade rewrote, once it has run. Count before.

**Undo cost.** Low for the schema: drop one constraint, one trigger and one function. None for
rows written afterwards, which hold nothing the old schema refused. The rewrite is not undone by
anything short of a backup: the kinds it replaced are gone.

**Impact.**
- *Security.* The one field of an answer read as a category can no longer carry text a model wrote,
  whichever statement wrote the entity.
- *Operations.* An upgrade across this migration holds writes to `entity` from the rewrite to the
  commit, and reads for one pass over the table while the check is validated. Both are the size of
  the entity table. An operator who wants to know what will change counts first.
- *Performance.* One comparison per entity written. Nothing on the read path.
