# D59 — An advisory the latest release calls is cleared within seven days

**Date.** 2026-11-12. **Issue.** [#225](https://github.com/ensera-ai/taisce/issues/225).

**Why it was open.** The latest release is scanned daily and a finding opens a public issue. What
followed a finding was not stated. `SECURITY.md` said so on purpose — a number nobody had agreed to
keep is worse than none — and that left an operator who read the issue knowing they were affected
and not knowing whether to wait a day or a quarter.

**Decided.**
- **The policy covers the latest release.** The answer to an affected release is a release that is
  not: the next patch on the current line, or the first of the next line if that is what the main
  branch has become. There are no maintenance branches, and an older release is not patched.
- **A finding is split by whether the release's own code calls the vulnerable code.** Called: a
  release that clears it is published within seven days of the scan's issue being opened, or of a
  fixed version of what is affected being published, whichever is later. Linked and not called: the
  next release clears it, with no date.
- **The split is made by something that runs.** `scripts/released-called.sh` checks the release's
  tag out and asks the reachability question of that source, with the toolchain the published binary
  names. Undecided — the scanner failed, the tag could not be read — is taken as called.
- **The date is on the issue from the moment it is opened**, computed by the scan from the same
  number `SECURITY.md` states. Kept or missed is the difference between two dates on a public page.

**Rejected: patching the previous line as well.** It is what an operator one release behind would
want. It needs a branch per line, a second release to cut and verify for every advisory, and a
second schema history to keep compatible — for one maintainer. An upgrade from one release to the
next rolls without an outage (D58), which is the answer given to that operator instead, and it is
one this project can keep.

**Rejected: a date for every finding.** The binary scan reports what was linked in. A promise on
that width would start a clock for code nothing here executes, several times a year, and a policy
that is routinely met by rebuilding for no reason teaches everyone that its issues are noise —
including the one that matters.

**Rejected: a date by severity score.** A score describes the advisory in general. Whether this
service calls the code is the part of severity that can be decided here, mechanically, for this
release; the rest is a judgement about deployments this project cannot see.

**Rejected: counting from the advisory's publication.** That date is somebody else's, and the scan
that notices is daily, so the difference is at most a day. The issue's opening is a moment on this
project's own public record, which is where a promise should be measurable.

**Rejected: no number.** The position until now. Honest, and it leaves the operator to guess.

**What it does not cover.**
- **Older releases**, as above.
- **The PostgreSQL image** a release publishes, which is not scanned.
- **An advisory with no fix yet.** The clock waits for one; nothing here can clear what upstream
  has not.
- **Exposure.** "Calls" means the release's code reaches the vulnerable symbol, not that a
  deployment can be reached through it.
- **Anything beyond one maintainer's word.** Every release waits for one person's approval. The
  number makes a miss visible; it does not make one impossible.

**Proof.** `TestAFindingSaysWhetherTheReleaseCallsWhatItCarries` holds where the question is asked
and with which toolchain, and that undecided is never read as "does not call".
`TestThePatchPolicyIsStatedOnceAndTheScanKeepsToIt` holds the document and the scan to one number.
Run for real on 2026-11-12: `make vuln-released RELEASE=v0.6.1` reported GO-2026-6859 in four of
four binaries built by go1.27.3, then `release v0.6.1: its own code calls the vulnerable code`; the
same command on v0.7.0 judged four binaries and found none affected. That advisory first failed
the tree's build on 2026-11-11 and v0.7.0 was published on 2026-11-12, so the one case there has
been was inside the number.

**Undo cost.** The script and the workflow lines are small to remove. The number is a public
promise: lengthening it is a visible retreat, and should be a new entry saying why.

**Impact.**
- *Security.* An operator on the latest release knows, from a public issue, whether a finding
  starts a clock and when it ends.
- *Operations.* A called advisory in the latest release is now work with a deadline, for the one
  person who approves releases.
