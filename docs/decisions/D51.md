# D51 — The chart publishes a surface as an Ingress or a Gateway route, and the console answers at its root

**Date.** 2026-11-12. **Issues.** [#204](https://github.com/ensera-ai/taisce/issues/204),
[#205](https://github.com/ensera-ai/taisce/issues/205).

**Why it was open.** Two things an operator met in the first hour. The hostname they were given for
the console answered `404` at its root, because only `/portal` was routed, and the first thing
anybody does with an address is open it. And on a cluster whose ingress is Gateway API the chart
could publish nothing: the operator wrote a route, a certificate reference and a grant by hand —
four objects, on the cluster where this was measured — and the grant is the one that goes wrong
quietly in both directions.

**Decided.**
- **Each surface is published as an `Ingress`, or as an `HTTPRoute` when `kind` says so.** One
  setting per surface; the two need not agree.
- **A route must name what it attaches to.** Empty `parentRefs` is refused at render: the cluster
  accepts such a route and it serves nothing.
- **The chart renders what attaches, never what is attached to.** No `Gateway`, no listener.
- **A certificate kept in this namespace is granted by name.** `certificateSecret` renders a
  `ReferenceGrant` from each gateway namespace in `parentRefs` to that one secret. There is no way
  to render a grant to the kind.
- **The console's hostname routes `/portal` and the exact path `/`, and nothing else.** The
  management API on the same port stays unpublished.
- **The redirect at the root is the management listener's own answer, not the route's.** With the
  portal on, `GET /` on that listener redirects to `/portal/`; every other unclaimed path is `404`.
- **The memory hostname's root is never the console's.** When both surfaces share a hostname the
  console's root rule is not rendered.

**Rejected: the redirect as a filter on the route.** A Gateway route can redirect by itself, and
that needs nothing from the binary. An `Ingress` cannot — the redirect there is a controller's
annotation, a different one per controller — so the two kinds would behave differently for the same
values, and the common one would have no root at all. Answering in the listener gives one behaviour
to both kinds and to a deployment with no ingress, where `localhost:8081/` now arrives too. The
location is relative, so the listener does not have to know the name or the scheme it was reached by.

**Rejected: a prefix rule at the root of the console's hostname.** It is the usual rule and it makes
the redirect trivial. It also sends every path on that hostname to the management listener, which
publishes the management API this arrangement exists to leave inside the cluster.

**Rejected: redirecting every unclaimed path into the console.** It answers a prober's whole
wordlist with where the console is, and serves no reader: an operator arrives at the bare name.

**Rejected: rendering the `Gateway` and its listener.** It would make a Gateway cluster a one-values
install. A listener belongs to whoever owns the gateway; a chart that writes one either demands a
gateway of its own per release, or edits a shared object it does not own and will delete on
uninstall.

**Rejected: a grant to the Secret kind**, which is what an example found first produces and what
works on the first try. It lets the gateway's namespace read every secret this namespace will ever
hold, which includes the database's role passwords.

**Rejected: deriving the network policy's caller from `parentRefs`.** The namespace of a `Gateway`
object is not always the namespace its proxy pods run in, and a policy admitting the wrong one
would install and time out. The operator names it, and an ingress with nobody admitted is refused
(D49).

**What it does not cover.**
- **The certificate.** The chart names a secret; what puts a certificate in it is the cluster's.
- **The listener's own settings** — hostname, `allowedRoutes`, the certificate reference. A listener
  that does not admit this namespace's routes leaves the route unattached, and the chart cannot see
  that.
- **An image older than this.** The root rule reaches a listener that answers `404`, as before.
- **Route kinds other than `HTTPRoute`.** The MCP endpoint and the memory API are plain HTTP.

**Proof.** `deploy/helm/gateway_test.go`:
`TestTheConsolesHostnameAnswersAtItsRootAndTheMemoryHostnameDoesNot`,
`TestAGatewayClusterPublishesEitherSurface`, `TestTheGatewayIsGrantedOneNamedSecretAndNeverTheKind`,
`TestARouteThatCouldNotServeIsRefused` — all four fail against the template as it was.
`TestTheConsolesListenerSendsItsBareRootToTheConsoleAndNothingElse` holds the listener. The routes
and grants rendered in the shape of a running deployment were accepted by a server-side dry run on a
cluster serving Gateway API v1.6.3 (2026-11-12). Not shown: a gateway serving through a route this
chart rendered — the deployment that was checked against is served by routes written by hand, of the
same shape.

**Undo cost.** Low. `kind` defaults to `Ingress`, so a deployment that never set it renders what it
did before plus the root rule. Removing the root redirect is one route in the binary.

**Impact.**
- *Operations.* A Gateway API cluster publishes from values. An operator opening the address they
  were given lands on the console.
- *Security.* The management API cannot be published by the console's route in either kind, and a
  gateway is granted one named secret or none.
